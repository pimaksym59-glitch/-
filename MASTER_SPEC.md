### §0.7 Глоссарий
**Канал** — независимая арендная единица (tenant) с собственным профилем/памятью. **Персона** —
текстовый голос автора. **Актёр** — визуальная личность для изображений. **Задача (task)** —
единица очереди. **Стадия** — тип задачи в пайплайне. **Hard gate** — блокирующая бинарная
проверка. **Soft score** — невязкая оценка для выбора кандидата. **Bandit** — политика выбора с
исследованием. **LEAD_TIME** — упреждение генерации перед слотом публикации.

**[R1.4]** Правило проверяемости: любое требование, которое нельзя проверить машиной, переводится в

### §1B Runtime Prompt (нормативно, ложится в код как шаблон)
**[R1.5] Уникальность:** каждый пост обязан отличаться структурой, началом, эмоциями, лексикой,
длиной, финалом, призывом — даже при одинаковой теме. Измеримо через §5.
**[R1.6] Человечность:** запрещены типовые AI-фразы, канцеляризмы, повторяющиеся конструкции,
одинаковые вступления/абзацы. Реализуется стоп-листом + LLM-judge (§5).
**[R1.7] Память контента:** каждый опубликованный пост → в память; перед новым постом проверяется
похожесть к окну истории (§5/§9).
**[R1.8] Персонажи по каналам:** выбор персонажа/актёра ограничен `channel_id`; смешение запрещено.
**[R1.9] Self-check перед публикацией:** грамматика, логичность, повторы, качество, уникальность,
читабельность, структура, соответствие стилю/языку. Провал → переписать (в пределах §5) или ревью.
**[R1.10] Fail-safe:** при недоступности любого внешнего модуля материал **не публикуется**; ошибка
сохраняется, владелец уведомляется, попытка повторяется по политике §Appendix B.

## §2. Architecture

**[R2.1] Стиль — модульный монолит** (ledger #1, REPORT #2): один код-базис, доменные модули как
пакеты с публичными интерфейсами; исполнение несколькими процессами (api/scheduler/worker) поверх
**общей очереди задач**. **Микросервисы запрещены** без отдельного согласования.
**[R2.2] Очередь-backbone:** источник истины — таблица `tasks` в PostgreSQL, разбор
`FOR UPDATE SKIP LOCKED`. Все тяжёлые операции — асинхронно через очередь.
**[R2.3] Модули (зоны ответственности):** AI · Content · Image · Telegram · Scheduler · Storage ·
Memory · RAG · Validators · Analytics · Notifications · Admin. «Сервис» = модуль, не отдельный деплой.
**[R2.4] Data flow:** Scheduler → очередь → AI(+Memory/RAG) → Validation → Image → Telegram →
Analytics → обновление памяти.
**[R2.5] Пайплайн — 5 стадий-задач** (см. §8/§13): `generate_text → validate → generate_image →
publish → collect_metrics`, связанных continuation-chaining (#28).
**[R2.6] Изоляция арендаторов** (REPORT #5): каждый запрос к данным скоупится `channel_id` (кроме
Global Memory). Смешение данных каналов запрещено без явной настройки.
**[R2.7] Масштабирование** (REPORT #6): горизонтальное — увеличением числа `worker`-процессов, без
изменения бизнес-логики. Профиль канала — в БД (#5), добавление канала не требует изменения кода.
**[R2.8] Потолок масштаба — внешние API, не CPU:** обязательны **пер-провайдерный распределённый
rate-limiter** (#42) и учёт стоимости на канал. Без rate-limiting рост упирается в 429.
**[R2.9] AI fallback-каскад:** основная модель → резервная → reschedule → уведомить владельца (§5).
**[R2.10] Провайдер-абстракции с фейками:** LLM/Image/Embedding/Telegram/Metrics — через
`get_*_provider(settings)`: реальный клиент при наличии ключа, иначе фейк. Вся система запускается и
тестируется **offline**.

## §3. Repository & Code Standards

**[R3.1] Правило слоёв** (ledger #3, REPORT #12/14): зависимости **строго вниз**
`api → services → (domain, repositories) → models/db`; циклы запрещены.
- `api/` — только маршруты; без бизнес-логики и SQL.
- `services/` — оркестрация сценария; без доменных правил генерации и без SQL.
- домен (`content/images/llm/telegram/memory/rag/validators/analytics/notifications`) — доменная
  логика и адаптеры провайдеров; **не открывает сессию БД, не знает HTTP**.
- `repositories/` — только запросы к БД; без доменных правил.
**[R3.2] ORM-модели** — централизованно в `app/models/` (один дом, #4). `db/` — `base/session/
migrations/seed`.
**[R3.3] Конфиг канала** — источник истины в БД (#5); `config/channels/*.yaml` — только seed/import.
**[R3.4] Загрузчик конфига** — единый Pydantic Settings в `app/core/config.py`; приоритет
БД(канал) > `.env` > `config.yaml`.
**[R3.5] Точки входа:** `app/main.py` (api), `app/scheduler/run.py`, `app/workers/run.py`.
**[R3.6] Конвенции:** файл ≤400–500 строк · 1 класс = 1 ответственность · функция ≤20–40 строк ·
понятные англ. имена · docstrings на сервис/публичный метод/pipeline/сложную функцию.
**[R3.7] Запрещено** (REPORT #12): дублирование · циклические зависимости · бизнес-логика в API ·
SQL в сервисах · секреты в коде · «магические» значения вместо конфигурации.
**[R3.8] Расширяемость** (REPORT #7): новый провайдер = новый файл-адаптер + регистрация в фабрике,
без изменения существующих модулей. Отдельный плагин-загрузчик — только по реальной потребности.
**[R3.9] Тесты** зеркалят структуру; пишутся **вместе** с кодом (не финальным этапом).

**[R4.3] UUIDv7** как PK минимум на insert-heavy таблицах (#8): `memory, images, api_usage,
image_usage, logs, errors, tasks, analytics_snapshots`.
**[R4.4] Soft delete + partial unique** (#9): естественные ключи — `UNIQUE(...) WHERE deleted_at IS NULL`.
**[R4.5] Эмбеддинги — колонка на владельце** (#6): `memory.embedding vector(N_text)`,

**[R4.6] Размерность эмбеддингов — платформенная константа** (#7, REPORT): не поле канала; смена

**[R4.7] Persona ≠ Actor** (#11): текстовый голос — `personas`; визуал — `actors`;

**[R4.8] Analytics — временной ряд** `analytics_snapshots` (#12), не единственная строка на пост.
**[R4.9] Очередь `tasks`** — enum'ы и колонки под `SKIP LOCKED` (§8), `dedup_key` для идемпотентности.
**[R4.10] Таблицы (полный перечень, DDL в DATABASE_SPEC):** channels, channel_settings, personas,
actors, locations, posts, post_history, images, image_history, prompts, schedules, tasks, memory,
topics, cta, analytics_snapshots, api_usage, image_usage, errors, logs, users,
**documents, document_chunks** (KB, #32), **audit_log, config_versions** (#37).
**[R4.11] Enum `task_status`:** `pending, running, succeeded, failed, deferred, needs_review,
cancelled, dead` (§7/§8).
**[R4.12] Enum `task_type`:** `generate_text, validate, generate_image, publish, collect_metrics,
backup, cleanup, reindex, health_check`.
**[R4.13] Enum `role`:** `owner, admin, editor, analyst, viewer` (#36).
**[R4.14] Индексы:** btree на FK/`status`/`published_at`/`run_at`; partial unique на естественных
ключах; GIN на jsonb и FTS (`to_tsvector`)+`pg_trgm`; **HNSW** на vector-колонках.
**[R4.15] Партиционирование по времени** — кандидат для `analytics_snapshots, api_usage,
image_usage, logs` при росте (не обязательно на старте).

## §5. AI Engine

**[R5.1] Стадии `generate_text`:** load persona/memory → topic → outline → draft → **self-review↔
rewrite loop** (внутри одной задачи). Затем отдельные задачи `validate`, `generate_image`.
**[R5.2] Сборка контекста** (#14, REPORT): «окно 500» — параметр `HISTORY_WINDOW` для **векторного
сравнения** (косинус, ноль токенов), в промпт **не попадает**. В промпт — **few-shot K=3–5** через
RAG + `persona.best_examples`. Сборщик соблюдает `MAX_CONTEXT_TOKENS`.
**[R5.3] Динамический prompt-builder:** промпт собирается из персоны + правил стиля + темы +
расписания + few-shot + ограничений (`forbidden_this_run`). Статический промпт на все случаи запрещён.
**[R5.4] Topic generation + diversity:** AI сам выбирает тему; жёсткие запреты — не >3 дней подряд
один тип, запрет повтора CTA/вступлений/выводов/историй (передаются в `validate`).
**[R5.5] Self-review = два независимых механизма** (#15): (1) rule-based hard gates (грамматика,
язык, длина, стоп-лист, структура) — мгновенный fail без LLM; (2) **отдельный** LLM-judge
(человечность, стиль, связность, эмоции) по рубрике 0–100.
**[R5.6] Rewrite** (#13): `MAX_REWRITES=3` (качество) ≠ `MAX_RETRIES=5` (инфра). Best-of-N с гейтом:
берём первый прошедший; если ни один за 3 — лучший по score → **ревью владельцу**, не публикуется.
**[R5.7] Duplicate cascade** (#18) дёшево→дорого: trigram Jaccard → предложения/абзацы → пост
целиком → story/CTA. Порог `SIMILARITY_THRESHOLD=0.85` → переписать.
**[R5.8] Humanization:** стоп-лист (gate) + judge-порог `HUMANNESS_MIN=75` (§R1.6).
**[R5.9] Quality score:** hard gates (язык/длина/стоп-лист, уникальность, человечность) блокируют
публикацию; soft scores (стиль, читаемость, связность, эмоции, CTA) — для выбора кандидата.
Публикация — только при прохождении **всех hard gates** (REPORT #3 — validation до publish).
**[R5.10] Model routing / fallback** (#17): тело/продающие = `claude-opus-4-8`; заголовок/CTA/тема/
judge = `claude-haiku-4-5`. Fallback: primary → fallback tier → reschedule → уведомить владельца.
Embedding-модель здесь не выбирается (платформенная, #7).
**[R5.11] Self-learning = bandit** (#16, §11): epsilon-greedy/Thompson с полом исследования
`epsilon_min`, медленное регуляризованное обновление. Крутит **только выбор** (§11 governance).
**[R5.12] Cost control:** стоимость каждого вызова пишется в `api_usage`.

## §6. Image Engine

**[R6.1] ⚠️ Постоянство лица актёра** (#19, REPORT #9) достигается **identity-conditioning по
референсам** (IP-Adapter/face-embedding/img2img) или per-actor LoRA — **не текстом и не seed**.
`actors.reference_images_folder` — **вход генерации**. Поддержка identity-conditioning — **критерий
выбора `image_provider`**. Мульти-актёрные сцены — отдельная более рискованная ветка.
**[R6.2] Актёры вымышлены:** запрещено воспроизводить внешность реальных людей.
**[R6.3] Разнообразие — до генерации** (#21): выбор сцены (локация/одежда/поза/ракурс/эмоция)
исключает значения из окон (`IMAGE_WINDOW=30` композиция/ракурс, гардероб ≥3, палитра ≥2). CLIP —
верификация **после**.
**[R6.4] Каскад похожести — 3 механизма** (#20): phash (почти-дубли) ≠ метаданные сцены (локация/
одежда/поза/ракурс) ≠ CLIP-эмбеддинг (семантика).
**[R6.5] Regen** (#22): `IMAGE_MAX_REGEN=3` (платно, качество/уникальность) ≠ `MAX_RETRIES=5`
(инфра). Исчерпан → ревью владельцу (или пост без фото, если канал разрешает).
**[R6.6] Сцена по времени слота:** набор сцен определяется `scheduled_at` (§8), случайные сцены
без учёта времени суток запрещены.
**[R6.7] Image validator:** лицо/руки/глаза/одежда/артефакты/реалистичность/**соответствие актёру**
(face-эмбеддинг vs референс). Провал → regen.
**[R6.8] Storage:** оригинал+миниатюра+промпт+negative+метаданные+CLIP+phash. Файлы — на диск/
**объектное хранилище** (S3-совместимое при росте, `storage_path`=ключ объекта).
**[R6.9] Провайдеры** (Nano Banana/Flux/OpenAI/Ideogram) — через единый интерфейс + фабрику; отказ
провайдера по контент-политике обрабатывается как сбой (fallback/деферал), не падение.

## §7. Telegram Engine

**[R7.1] Транспорт — Bot API/aiogram** (#23); MTProto — опциональный адаптер за тем же интерфейсом.
Постинг user-аккаунтом запрещён (ToS/бан-риск). Бот — **админ канала**.
**[R7.2] ⚠️ Нет серверного планирования** (#24, REPORT #4): время держит **наша очередь** (`run_at`);
`publish` шлёт немедленно в момент слота.
**[R7.3] ⚠️ Bot API не отдаёт просмотры/реакции постов** (#25, REPORT #4): метрики views/ER/CTR
недоступны без MTProto stats-адаптера (§Appendix C). Дашборд не показывает недоступные метрики
выдуманными значениями (§10/§11).
**[R7.4] ⚠️ Публикация at-least-once** (#26): при неоднозначном сбое (запрос ушёл, ответа нет) —
статус `needs_review`, **без авто-ретрая**; `dedup_key` фиксируется до отправки.
**[R7.5] Retry:** `MAX_RETRIES=5`+backoff; **429 → honor `retry_after`**; перманентные ошибки
(bad token/kicked/no rights/конфиг) — без ретрая, сразу владельцу.
**[R7.6] Rate limits пер-бот** (#27, REPORT #6): ~30 msg/s суммарно, ~1/s на чат; при масштабе —
**отдельный bot-токен на канал/группу**. Ключ лимитера — `bot_token`+`channel_id` (распределённый, #42).
**[R7.7] Форматтер:** MarkdownV2/HTML с экранированием; лимиты — текст ≤4096, **подпись медиа ≤1024**
(gate в `validate`).
**[R7.8] Режимы:** текст/фото/альбом(1–10)/видео/документ; **draft** (без публикации), **approval**
(стоп перед publish, ревью владельца).
**[R7.9] Edit/Delete/Pin:** edit → новая версия в `post_history`; delete — после проверки прав +
журнал (soft); pin/unpin/replace/auto-unpin.
**[R7.10] Очередь на канал — логическая** (одна `tasks` + справедливый SKIP LOCKED против голодания),
не N физических очередей. Недоступность одного канала не блокирует другие.

## §8. Scheduler & Automation

**[R8.1] Scheduler = продюсер, воркеры = исполнители.** Scheduler материализует задачи из `schedules`
и периодические сценарии в `tasks` с `run_at`; **без бизнес-логики**.
**[R8.2] Task types/statuses — канонические** (REPORT #4/11): типы §R4.12, статусы §R4.11. Новый тип
= обработчик в реестре + enum-миграция.
**[R8.3] Lifecycle:** `created→pending→running→succeeded`; `failed→(attempts<MAX)deferred→pending`;
`(attempts=MAX)→dead`; `→cancelled`.
**[R8.4] Зависимости = continuation-chaining** (#28): каждый обработчик на успехе ставит следующую
стадию; сбой → цепочка не продолжается. DAG-движок — только при реальном ветвлении.
**[R8.5] LEAD_TIME** (#29, REPORT #3): слот в `schedules` = время публикации;
`generate_text.run_at = slot − LEAD_TIME` (деф. 30–60 мин, конфиг); `publish.run_at = slot`. Не
уложились → деферал на ближайшее валидное окно.
**[R8.6] Timezone:** хранение UTC, расчёт слота в IANA-tz канала. Правило DST фиксировано
(несуществующий слот → сдвиг вперёд; двойной → первое вхождение).
**[R8.7] Publication windows:** задача вне окна → `deferred` на ближайшее валидное, не отбрасывается.
**[R8.8] Priority:** `critical/high/normal/low`; разбор `ORDER BY priority, run_at`; справедливость
между каналами.
**[R8.9] Concurrency limits** (#42): семафор/token-bucket **распределённый (Redis)** по ключу
провайдера; лимиты на `task_type` и на провайдера; защита от 429.
**[R8.10] Мульти-инстанс** (#30): воркеры безопасны через SKIP LOCKED; продюсер — идемпотентный
`UNIQUE(channel_id, schedule_id, slot_datetime)` + `pg_advisory_lock`. Leader election не обязателен.
**[R8.11] DLQ = статус `dead`** (после `MAX_RETRIES`): причина сохранена, уведомление, ручной requeue.
**[R8.12] Автоматизация/обслуживание:** ежедневная генерация, backup, `cleanup` (VACUUM/ANALYZE),
`reindex`, `health_check` — периодические задачи канонических типов.
**[R8.13] Holiday support:** календарь событий на канал → выбор контент-плана (влияет на §5),
scheduler только координирует.
**[R8.14] Pause/Resume:** пауза задачи/канала(`paused`)/типа; возобновление без потери очереди
(состояние в Postgres).

## §9. Memory, Knowledge Base & RAG

**[R9.1] Уровни памяти:** Global (кросс-канальный, единственный) · Channel · Persona · Content
(`memory` kind=published_post) · Image (`images` метаданные) · Analytics (`analytics_snapshots`).
**[R9.2] Изоляция канала = hard filter** (#31, REPORT #5): каждый векторный/поисковый запрос
содержит `WHERE channel_id` (кроме Global). Это безопасность, **не** вес реранкинга.
**[R9.3] Knowledge Base ≠ Content Memory** (#32): справочные знания в `documents`/`document_chunks`
(версионирование), история постов — в `memory`. Не смешивать.
**[R9.4] Document ingestion — прямой вызов, не задача** (не плодим enum). Этапы: формат→текст→
очистка→**семантический chunking**→эмбеддинги→индексация→метаданные.
**[R9.5] Chunking** — по смысловым блокам (не по символам), целевой размер под окно embedding-модели
с перекрытием; **чистая логика, юнит-тесты**.
**[R9.6] Embeddings** — единая платформенная размерность в индексе (#7); смена модели =
батч-переиндексация.
**[R9.7] Retrieval + reranking:** hard filters (channel, тип документа, **активная версия**) до
ранжирования; soft ranking (близость темы, опц. cross-encoder, свежесть, доверие) — после.
**[R9.8] Context assembly:** компактно ≤`MAX_CONTEXT_TOKENS`; few-shot K=3–5 (#14), не 500.
**[R9.9] Retention:** тиры active/archive/purge; опубликованное и важные знания всегда искомы;
retention держит HNSW быстрым (не только диск).
**[R9.10] Knowledge versioning:** при обновлении — старая версия сохраняется, новая индексируется,
`active_version` помечается; retrieval берёт активную.
**[R9.11] Search modes:** семантический · ключевые слова (FTS/`pg_trgm`) · гибрид (RRF) · по типу.
**[R9.12] Style Memory** (#33): хранит **признаки стиля** (длины предложений, частота диалогов,
структура абзацев, эмоц. динамика, обороты, переходы), не тексты; jsonb (+опц. style-эмбеддинг);
промпт инжектит параметры, а не старые посты. Сложные признаки — по готовности экстрактора.
**[R9.13] Observability:** на запрос — время поиска, найдено/использовано, время сборки, объём контекста.

## §10. Admin Panel & Control Center

**[R10.1] Панель = клиент `services`/`api`** (#34): ручные операции идут через **ту же очередь**
(«опубликовать» = задача `publish`; «перегенерировать» = `generate_text/generate_image`). Второй
путь публикации запрещён.
**[R10.2] Frontend:** серверный рендер + HTMX по умолчанию (внутренний ops-инструмент); API — чистый
JSON, SPA опционально позже. (Реализационное решение, не архитектурное.)
**[R10.3] Аналитика показывает только доступное** (#35, REPORT #4): недоступные на Bot API метрики
(views/ER/CTR/реакции) скрыты или помечены «требует MTProto-адаптера», не показываются выдуманными.
**[R10.4] Auth:** защищённый вход, MFA (опц.), сессии, журнал входов, принудительное завершение.
Секреты/ключи — **write-only поля**, никогда не отображаются (§12).
**[R10.5] Роли — 5** (#36): `owner/admin/editor/analyst/viewer`. **RBAC на бэкенде** (`api`/`services`);
UI-скрытие не является защитой.
**[R10.6] Разделы:** Dashboard · Channel/Settings · Persona · Image · Content · Knowledge · Prompt ·
Scheduler/Task Monitor (статусы §R4.11, DLQ requeue) · Log Viewer · Analytics · **Cost** · Health ·
Search · Bulk · Export/Import · API Management · Notification Center.
**[R10.7] Bulk-операции** уважают пер-бот лимиты (#27): ставят задачи в очередь, не fire-and-forget;
массовое удаление — soft.
**[R10.8] Audit & versioning** (#37): `audit_log` (все действия) + `config_versions` (снапшоты для
сравнения/отката). Без них аудит/откат нереализуемы.
**[R10.9] AI Studio — изолирован** (#38): тест промптов/сравнение LLM/dry-run/оценка стоимости;
**не пишет в память каналов и не публикует**.

## §11. Analytics, Self-Learning & Optimization

**[R11.1] Надёжная аналитика — внутренняя:** Cost/Quality/System/Content-diversity не зависят от
Telegram engagement и всегда доступны. Engagement (views/ER/CTR) — **gated** (§R7.3).
**[R11.2] Analytics не решает за AI Engine** — предоставляет данные и рекомендации; рекомендации,
меняющие стратегию канала, **не применяются автоматически**.
**[R11.3] Сигнал обучения:** без MTProto-адаптера — рост подписчиков (`getChatMemberCount`), клики по
трекинг-ссылкам, прокси (quality/uniqueness/regen). Сигнал слабый/шумный → обучение медленное (§5).
**[R11.4] Governance-граница** (#40): bandit авто-крутит **выбор** (темы/CTA/структура/время) с полом
исследования; **запрещено авто-менять** базовый стиль, персону, ключевые правила, системные промпты
— только через администратора.
**[R11.5] ⚠️ A/B со сплитом аудитории невозможен** (#39, REPORT #7): канал вещает всем один пост.
Доступны только **temporal** и **cross-channel** эксперименты (с confounding); результаты — гипотезы.
**[R11.6] Experiment Manager:** temporal/cross-channel эксперименты; результаты хранятся отдельно от
основной статистики; безопасное вкл/выкл; пре-прод — в AI Studio (§10).
**[R11.7] Разделы:** report generation (задачи планировщика), channel report, content/image/CTA/
style-consistency/schedule/error/cost analysis, trend detection, quality dashboard, recommendation
engine. Style-consistency = обратная связь для Style Memory (§9).
**[R11.8] Cost forecasting** — надёжный высокоценный выход (из `api_usage`/`image_usage`).
**[R11.9] Observability:** каждый расчёт — дата, источник, фильтры, **версия алгоритма**, время.

## §12. Security, DevOps & Production Infrastructure

**[R12.1] Environments:** Development/Testing/Staging/Production — свои env/БД/конфиг/ключи/логи/
мониторинг. Продвижение только через CI/CD.
**[R12.2] Secrets** (#44, REPORT #8): вне кода/репозитория; в проде — **secret manager / Docker
secrets**, не plaintext `.env`; не в логах (маскирование); не в панели (§R10.4); БД — **least-privilege**.
**[R12.3] Контейнеры = роли одного образа** (#41): `api`(+admin HTMX), `scheduler`, `worker`(×N) —
один образ, разные команды; инфра — postgres(pgvector), redis, reverse proxy. Не микросервисы.
**[R12.4] Container principles:** одна функция · healthcheck · минимальный размер · graceful
shutdown (воркер дорабатывает текущую задачу).
**[R12.5] Reverse proxy / HTTPS / network:** прокси (Caddy — auto-TLS, дефолт) даёт HTTPS/
маршрутизацию/rate-limit/security-заголовки; наружу — **только прокси**; postgres/redis/worker/
scheduler — во внутренней сети.
**[R12.6] Migrations:** только Alembic; ручное изменение схемы на проде запрещено. Горячие таблицы —
**expand-contract** + `CREATE INDEX CONCURRENTLY` (#43), условие 24/7.
**[R12.7] Backup:** БД (`pg_dump`+PITR/WAL), изображения (object storage), конфиги, KB, вектора,
метаданные; ежедн./еженед./ежемес.; срок хранения настраивается; бэкапы шифруются.
**[R12.8] Restore:** проверяется регулярно на staging (полная/БД/канал/документы/изображения).
Непроверенный бэкап = отсутствие бэкапа.
**[R12.9] Logging:** структурированный JSON — время/уровень/сервис/`request/task_id`/`channel_id`/
событие; уровни DEBUG/INFO/WARNING/ERROR/CRITICAL. Audit log отдельно (§R10.8).
**[R12.10] Monitoring/Health/Alerting:** liveness ≠ readiness (разные эндпоинты); мониторинг
сервисов/нагрузки/очередей/ошибок API/Telegram; алерты (Scheduler down, БД down, backup fail,
mass publish errors, disk full) с **внешним dead-man's-switch** (мёртвый scheduler не алертит сам).
**[R12.11] Resource limits:** память/CPU/процессы/соединения на контейнер.
**[R12.12] CI/CD:** format(ruff/black) → static(ruff, **mypy**) → tests(pytest; unit всегда,
интеграционные за `RUN_INTEGRATION=1`) → build → **migration check** → deploy. Деплой только после
всех проверок.
**[R12.13] Dependencies:** фиксированные версии (`uv` lock); обновления через тестирование.
**[R12.14] MTProto stats-адаптер** (если введён, §Appendix C) — под усиленным контролем: session-
файл как секрет, отдельная изоляция, только чтение.
**[R12.15] Deployment воспроизводим:** новый сервер по документированной процедуре с минимумом
ручных шагов; инструкции: запуск/обновление/восстановление/backup/перенос/диагностика.
