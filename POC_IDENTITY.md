# POC_IDENTITY.md — Proof of Concept: постоянство внешности актёра (T-3)

**Тип:** план будущего эксперимента (не реализация). **Статус:** Planned.
**Связано:** MASTER_SPEC §R6.1, §R6.7, DOCUMENT_AUDIT_V2 T-3, §R13.1 шаг 15 (Image Engine).
**Зачем:** §R6.1 утверждает, что постоянство лица достигается **identity-conditioning по референсам
или per-actor LoRA, а не текстом/seed**. Это ключевая непроверенная гипотеза всего проекта: без её
подтверждения «канал ведёт один узнаваемый персонаж» нереализуемо. POC должен доказать/опровергнуть
достижимость до реализации Image Engine.

> POC блокирует только §15 (Image Engine), не старт (§R13.1 шаги 1–12 от него не зависят).

---

## 1. Критерии успеха (цель POC)

POC считается **успешным**, если найдена **хотя бы одна** связка «провайдер + метод conditioning»,
которая при фиксированном наборе референсов актёра выдаёт изображения, где:

- лицо **узнаваемо то же** в широком диапазоне сцен (поза/локация/свет/одежда/ракурс),
- при этом сцены **разнообразны** (не деградируют в один кадр ради сходства лица),
- качество приемлемо (без грубых артефактов лица/рук),
- стоимость и латентность совместимы с масштабом (§R2.8).

Явный **отрицательный** исход (ни одна связка не проходит) — тоже валидный результат POC: он меняет
продуктовое допущение и эскалируется владельцу.

---

## 2. Рассматриваемые провайдеры и методы

**Методы conditioning (ортогонально провайдеру):**
- **Face/identity-adapter** (IP-Adapter-FaceID / InstantID / PuLID и аналоги) — лицо из
  face-эмбеддинга референсов.
- **Reference / img2img** — опорное изображение как вход.
- **Per-actor LoRA / fine-tune** — обучение лёгкого адаптера на референсах актёра (дороже в
  подготовке, обычно стабильнее).

**Провайдеры (кандидаты §R6.9):**
| Провайдер | Ожидаемый механизм identity | Примечание (проверить) |
|---|---|---|
| Nano Banana (Gemini image) | reference/editing | поддержка мульти-референса — проверить |
| Flux | IP-Adapter / reference / LoRA | часто лучший для identity-адаптеров |
| Ideogram | character reference | зрелость character-consistency — проверить |
| OpenAI Images (gpt-image-1) | image input / editing | стабильность лица между сценами — проверить |

> Конкретные названия эндпоинтов/фич меняются — на этапе POC уточняются по актуальной документации.
> Провайдер **без** identity-conditioning из сравнения исключается (не удовлетворяет §R6.1).

---

## 3. Методика тестирования

1. **Подготовка актёра:** зафиксировать 1 вымышленного актёра (§R6.2 — не реальный человек) с
   набором **референсов** (напр. 3–8 изображений одного лица с разных ракурсов).
2. **Матрица прогонов:** для каждой связки (провайдер × метод) сгенерировать **весь набор тестовых
   сцен** (раздел 4), по K образцов на сцену (напр. K=3) для оценки стабильности.
3. **Фиксация переменных:** одинаковые сцены/промпты между связками; варьируется только
   провайдер/метод. Seed логируется, но **не** считается механизмом идентичности (§R6.1).
4. **Измерение:** для каждого изображения посчитать метрики раздела 5 автоматически; лицо — через
   независимую face-модель (напр. ArcFace/InsightFace), **не** ту, что использовалась в conditioning
   (чтобы не мерить самого себя).
5. **Слепая экспертная оценка (доп.):** человек-ранжирование «тот же человек? да/нет» вслепую к
   провайдеру, как калибровка порога метрики.
6. **Сводка:** таблица связок × метрик; сравнение с критериями принятия (раздел 6).

Всё в изоляции от прод-каналов (аналог AI Studio §R10.9): без публикации, без записи в память.

|---|---|---|---|---|---|

помечен как высокорисковый (§R6.1).

## 5. Метрики оценки

- **Face-similarity (главная):** косинус face-эмбеддинга изображения к **центроиду референсов**
  актёра (независимая модель). Считается на каждый образец.
- **Identity-consistency:** средняя face-similarity по всем сценам + **дисперсия** (низкая
  дисперсия = стабильно узнаваем).
- **Scene-diversity:** попарная CLIP-непохожесть между сценами + покрытие метаданных (локация/поза/
  ракурс/палитра различны) — чтобы идентичность не достигалась «одинаковыми кадрами».
- **Artifact-rate:** доля кадров с грубыми дефектами лица/рук/глаз (авто-детектор + выборочная ручная).
- **Cost / latency:** $ и мс на изображение (§R2.8, §Appendix B учёт).
- **Refusal-rate:** доля отказов провайдера по контент-политике (§R6.9).

## 6. Критерии принятия

Связка «провайдер+метод» **проходит**, если одновременно (пороги — **предварительные, калибруются**
слепой оценкой раздела 3.5, т.к. абсолютные значения зависят от face-модели):

- **Identity:** ≥ **90%** тестовых сцен имеют face-similarity ≥ порога «тот же человек»
  (порог задаётся калибровкой, а не выдуман);
- **Consistency:** дисперсия face-similarity ниже установленного предела (нет «срывов» на отдельных сценах);
- **Diversity:** scene-diversity не ниже минимума (идентичность **не** за счёт однообразия);
- **Quality:** artifact-rate ≤ установленного предела;
- **Ops:** cost/latency/refusal-rate в приемлемых границах для масштаба.

**Решение по POC:** выбрать связку с лучшим балансом identity×diversity×quality×cost. Если ни одна
не проходит — эскалация владельцу (пересмотр допущения о фотореалистичном постоянном персонаже:
напр. стилизация, меньше крупных планов, композитинг).

## 7. Возможные риски

- **Ни один провайдер не проходит** — фундаментальный риск замысла; план Б: стилизованный визуал
  вместо фотореализма, ограничение крупных планов, LoRA-путь.
- **Мульти-актёрные сцены** — постоянство нескольких лиц в кадре заметно сложнее; вероятен путь
  «композитинг из одиночных генераций», а не единый кадр.
- **Контент-политика провайдеров** — отказы на фотореалистичных людей (§R6.9) искажают выборку и
  ограничивают продакшн.
- **Метрика лица несовершенна** — face-эмбеддинг может «прощать» разные лица или наоборот; поэтому
  порог калибруется слепой экспертной оценкой, а не берётся абсолютным.
- **Overfitting к референсам** — высокое сходство только на позах, близких к референсам; тестовые
  сцены специально уводят от них (S2/S4/S6).
- **Этика/likeness** — только вымышленные лица (§R6.2); референсы — сгенерированные/лицензированные,
  не фото реальных людей.
- **Дрейф API** — фичи провайдеров меняются; POC фиксирует дату и версии.

---

## 8. Результат POC (заполняется по завершении)

Таблица связок × метрик, выбранная связка (или отрицательный вердикт), рекомендованный
`image_provider` по умолчанию (§R6.9), калиброванный порог identity → в `channel_settings`/конфиг.
До завершения POC реализация §15 (Image Engine) на конкретном провайдере **не начинается**.
