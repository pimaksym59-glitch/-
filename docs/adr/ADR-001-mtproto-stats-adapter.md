# ADR-001. MTProto Stats Adapter (открытое решение O-1)

**Статус:** Proposed (рекомендация; решение — за владельцем, §R0.4/R0.5)
**Дата:** 2026-07-22 · **Связано:** MASTER_SPEC §R7.3, §R11.3, §R11.5, §R10.3, §R12.14, §Appendix C
**Контекст:** Bot API **не отдаёт** просмотры/реакции постов канала (§R7.3). Без них per-post
ER/CTR недоступны, а self-learning (§R11.3) опирается лишь на рост подписчиков, клики по ссылкам и
прокси (quality/uniqueness/regen) — слабый шумный сигнал. Вопрос: вводить ли отдельный источник
статистики.

> ⚠️ Конкретные возможности Telegram API (доступ бота к `stats.getBroadcastStats` и полю
> `message.views` через MTProto по bot-токену, пороги активации статистики канала) **подлежат
> проверке спайком** перед принятием — ниже они помечены как «ожидается/проверить».

---

## Рассматриваемые варианты

### Вариант A — Без адаптера (только Bot API) — **текущий дефолт**

**Описание.** Постинг и всё чтение — через Bot API. Аналитика ограничена доступным: рост
подписчиков (`getChatMemberCount`, снимки), клики по трекинг-ссылкам (UTM/редирект), внутренние
прокси-метрики. Per-post views/ER/CTR не собираются; в дашборде помечены недоступными (§R10.3).

- **Преимущества:** ноль дополнительной интеграции; ноль ToS-риска сверх Bot API; нет второго
  клиента/сессии-секрета; минимум кода и сопровождения; полностью offline-тестируемо (фейки).
- **Недостатки:** self-learning bandit слаб (нет per-post награды); атрибуция «какой пост
  сработал» практически невозможна; аналитический дашборд без engagement.
- **Влияние на архитектуру:** нулевое (уже заложено).
- **Влияние на безопасность:** нейтральное (нет новых секретов/поверхностей).
- **Влияние на стоимость:** нулевое.
- **Влияние на сопровождение:** минимальное.
- **Риски:** продуктовый — «самооптимизация» существует номинально; ожидания владельца могут
  разойтись с реальностью.

### Вариант B1 — MTProto stats **по bot-токену** (только чтение)

**Описание.** Отдельный read-only адаптер за интерфейсом провайдера метрик (§R2.10), использующий
**bot-токен** (не user-аккаунт) через MTProto для чтения `message.views`/broadcast-stats у каналов,
где бот админ. Постинг остаётся на Bot API (§R7.1).

- **Преимущества:** полноценный per-post сигнал (views, пересылки, динамика) → рабочий bandit
  (§R5.11) и honest-дашборд; **не** user-аккаунт → существенно ниже ToS-риск, чем B2; изолирован
  за интерфейсом, включается флагом.
- **Недостатки:** доступность bot-token MTProto к stats — **ожидается, требует проверки**; статистика
  канала активируется Telegram только после порога подписчиков/активности (ожидается) → для малых
  каналов данных не будет; второй транспорт (MTProto-клиент).
- **Влияние на архитектуру:** новый провайдер метрик + `collect_metrics` пишет реальные `views/er`
  в `analytics_snapshots` (NULLABLE-поля уже заложены, DATABASE_SPEC); отдельный контейнер/адаптер.
- **Влияние на безопасность:** bot-токен уже секрет; MTProto-сессия/`api_id/api_hash` — **новые
  секреты** → secret manager, изоляция (§R12.14). Только чтение — минимальные права.
- **Влияние на стоимость:** близко к нулю по деньгам (нет платного API); небольшой операционный overhead.
- **Влияние на сопровождение:** умеренное (доп. клиент, обработка флуд-лимитов MTProto, порогов stats).
- **Риски:** возможность по bot-токену не подтверждена (может потребовать B2); флуд-лимиты MTProto;
  изменения Telegram API.

### Вариант B2 — MTProto stats по **user-сессии** (только чтение)

**Описание.** То же, но аутентификация **user-аккаунтом** (телефон/сессия). Максимальная широта
данных (полная statistics-подсистема), но аккаунт-автоматизация.

- **Преимущества:** самый широкий доступ к статистике; гарантированно покрывает то, чего нет у бота.
- **Недостатки/риски:** **user-аккаунт под автоматизацией — риск ToS/бана** даже на чтении; сессия
  — чувствительный секрет; телефон/номер на канал/группу; операционно самый хрупкий вариант.
- **Влияние на безопасность:** максимальное — компрометация сессии = доступ к аккаунту.
- **Оценка:** не рекомендуется, кроме случая, когда B1 доказанно недостаточен и владелец принимает риск.

### Вариант C — Внешняя аналитика (сторонний сервис / только прокси)

**Описание.** Полагаться на прокси-сигналы (клики, рост подписчиков) + опционально сторонний сервис
статистики Telegram-каналов (агрегаторы) вместо собственного MTProto.

- **Преимущества:** без собственного MTProto-транспорта; быстрый старт.
- **Недостатки:** сторонние сервисы — новая зависимость, стоимость подписки, приватность данных
  каналов у третьей стороны, покрытие только публичных каналов; прокси-сигнал остаётся слабым.
- **Влияние на безопасность/приватность:** передача данных о каналах внешней стороне — нежелательно.
- **Оценка:** запасной путь, не основной.

## Рекомендация

**Отложенное включение B1 (MTProto stats по bot-токену), при старте — A.**

1. Начать разработку по **Варианту A** (дефолт) — он не блокирует ядро (§1–§9) и уже заложен.
2. Запланировать **спайк** для проверки B1: доступен ли `message.views`/broadcast-stats по
   bot-токену, каковы пороги активации и флуд-лимиты.
3. Если спайк успешен и владельцу нужен per-post сигнал — включить B1 (флагом, изолированно,
   §R12.14). B2 — только если B1 доказанно недостаточен и владелец принимает ToS-риск.
4. C — не выбирать как основной источник.

Решение — за владельцем; ADR фиксирует варианты и рекомендацию, не выбирает.

## Последствия принятия

- **Если A:** MASTER_SPEC §R11.3/R11.5 остаются в силе «как есть»; bandit работает на слабом
  сигнале; дашборд честно помечает engagement недоступным. Изменений в схеме нет.
- **Если B1:** активируется §R12.14; `analytics_snapshots.views/er/ctr` наполняются; bandit
  получает per-post награду; добавляется контейнер/секреты MTProto; TEST_PLAN дополняется тестами
  адаптера (фейк MTProto). Требуется предварительный спайк.
- **Если B2:** дополнительно — регламент защиты user-сессии и принятие ToS-риска владельцем (запись
  в Changelog §0.6).
