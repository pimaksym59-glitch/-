# ADR-002. Production Deployment Environment (открытое решение O-2)

**Статус:** Proposed (рекомендация; решение — за владельцем, §R0.4/R0.5)
**Дата:** 2026-07-22 · **Связано:** MASTER_SPEC §12 (весь), §R2.7 (масштаб), §R6.8 (object storage),
§R12.5 (proxy/TLS), §R12.2 (secrets), §Appendix C
**Контекст:** архитектура — модульный монолит с несколькими процессами поверх Postgres-очереди
(§R2.1). Требуется выбрать целевую среду. Выбор определяет reverse proxy, secret manager, пул
соединений, объектное хранилище, стратегию бэкапа и масштабирование воркеров.

---

## Рассматриваемые варианты

### Вариант A — Одна VM + Docker Compose + Caddy — **текущий дефолт**

**Описание.** Все контейнеры (api, scheduler, worker×N, postgres+pgvector, redis, caddy) на одной
VM через Compose. Caddy — auto-TLS. Бэкапы — cron `pg_dump`+WAL, изображения на локальном диске
или S3-совместимом бакете. Секреты — Docker secrets/`.env` с ограниченным доступом.

- **Преимущества:** минимальная сложность и стоимость; самый быстрый старт; воспроизводимо
  (`docker compose up`); полностью соответствует §R12.3 (роли одного образа); один хост — простая
  отладка/логи.
- **Недостатки:** вертикальный потолок (одна машина); БД/Redis самоуправляемы (бэкап/патчи на нас);
  единая точка отказа; горизонтальный масштаб воркеров ограничен ресурсами хоста.
- **Влияние на архитектуру:** нулевое сверх заложенного; распределённый rate-limiter (§R7.6/R8.9)
  на локальном Redis работает.
- **Влияние на безопасность:** приемлемо — наружу только Caddy (§R12.5); но патчи ОС/БД и изоляция
  сетей — на операторе.
- **Влияние на стоимость:** самая низкая (одна VM + опц. бакет).
- **Влияние на сопровождение:** простое на малом масштабе; растёт при увеличении числа каналов
  (ручное вертикальное масштабирование, ручные бэкапы БД).
- **Риски:** SPOF; исчерпание ресурсов при росте до сотен каналов; человеческий фактор в бэкапах.

### Вариант B — Облако managed (managed Postgres/Redis + object storage + container runtime)

**Описание.** Managed PostgreSQL (с pgvector) и Redis, объектное хранилище (S3/GCS) для изображений
и бэкапов, контейнеры в managed-runtime без K8s (напр. ECS/Cloud Run/Container Apps). Секреты —
облачный secret manager. TLS/LB — облачные.

- **Преимущества:** managed БД снимает бэкап/PITR/патчи/HA (§R12.7/R12.8 частично из коробки);
  object storage решает §R6.8 «сотни тысяч изображений»; secret manager (§R12.2) нативно;
  горизонтальный масштаб воркеров без ручного управления хостом; нет SPOF по БД.
- **Недостатки:** выше стоимость; привязка к провайдеру (vendor lock-in); больше движущихся частей
  в конфигурации; distributed rate-limiter требует managed Redis (есть).
- **Влияние на архитектуру:** минимальное к коду (12-factor уже соблюдён §R3.4/R12.2); меняется
  инфра-обвязка, не бизнес-логика (§R2.7).
- **Влияние на безопасность:** лучше базово (managed патчи, secret manager, приватные сети, IAM),
  но новая поверхность — облачные права/IAM-мисконфиги.
- **Влияние на стоимость:** заметно выше A; предсказуемо масштабируется.
- **Влияние на сопровождение:** ниже операционная нагрузка на БД/бэкапы; выше требования к
  cloud-экспертизе и контролю расходов.
- **Риски:** lock-in; рост счёта; IAM-ошибки.

### Вариант C — Kubernetes (оркестрация)

**Описание.** Полноценный K8s: деплойменты api/scheduler/worker, HPA для воркеров, managed или
in-cluster Postgres/Redis, Ingress+cert-manager, секреты через K8s Secrets/External Secrets.

- **Преимущества:** максимальная эластичность (HPA воркеров под §R2.7), self-healing, стандартные
  оркестрационные практики; хорош для многих узлов/высокого масштаба.
- **Недостатки:** высокая сложность и порог входа; избыточен для монолита с очередью на старте;
  операционная нагрузка (кластер, сеть, апгрейды); дороже в сопровождении.
- **Влияние на архитектуру:** к коду минимальное; к эксплуатации — существенное.
- **Влияние на безопасность:** мощные механизмы (network policies, RBAC k8s), но большая поверхность
  и много способов ошибиться.
- **Влияние на стоимость:** высокая (кластер + экспертиза).
- **Влияние на сопровождение:** самое тяжёлое; оправдано только на большом масштабе.
- **Риски:** переусложнение (нарушает §R3.8 «не спекулятивно»); нехватка k8s-экспертизы.

---

## Рекомендация

**Старт — A; путь роста — B; C отложить.**

1. Начать и до первых реальных нагрузок работать на **A** (одна VM + Compose + Caddy) — совпадает с
   дефолтом §Appendix C, минимальная стоимость и сложность.
2. С ростом до сотен каналов или при появлении требований HA/бэкапа-как-сервиса — мигрировать на
   **B** (managed). Код к этому готов (12-factor), меняется только инфра-обвязка (§R2.7).
3. **C (K8s)** — не вводить, пока B не упрётся в реальный потолок; иначе нарушается принцип «без
   спекулятивной сложности» (§R3.8).

Точка перехода A→B определяется числом каналов, стоимостью и требованием доступности — фиксируется
позже метриками, не сейчас.

## Последствия принятия

- **Если A:** §12 реализуется как есть; на операторе — бэкапы/патчи/мониторинг диска; object
  storage опционален на старте (порог §R6.8).
- **Если B:** managed Postgres/Redis + object storage обязательны; secret manager вместо `.env`
  (§R12.2 усилен); документация деплоя (§R12.15) описывает облачную процедуру; бэкап частично
  делегирован провайдеру, но restore-проверка (§R12.8) остаётся на нас.
- **Если C:** добавляется слой оркестрации, манифесты, HPA; §R12.11 (resource limits) переходит в
  k8s requests/limits; операционная документация существенно расширяется.
