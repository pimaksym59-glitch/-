# Часть 10. Admin Panel & Control Center

> Продолжает [Часть 9](09-memory-rag.md). Панель — **клиент того же слоя `services`/`api`**
> ([Часть 3](03-repository-structure.md)), а не второй путь публикации. Разрешает открытый
> вопрос аналитики из [Части 7](07-telegram-engine.md).

## GLOBAL OBJECTIVE

Единая точка управления всей платформой без изменения кода. Удобная, безопасная, масштабируемая
на десятки–сотни каналов.

---

## Принцип №1: панель ничего не реализует заново

Все действия панели идут через **существующие `services`/`api/v1`** — никакой параллельной
бизнес-логики:

- «Опубликовать вручную» → поставить задачу `publish` в очередь (Часть 8), **не** отдельный send;
- «Перегенерировать» → задача `generate_text`/`generate_image`;
- «Утвердить/отклонить» (approval mode, Часть 7) → смена статуса задачи `needs_review`.

Один код-путь для авто- и ручных операций. Иначе ручной постинг обойдёт валидацию/лимиты.

## Решение по фронтенду

Панель — **внутренний ops-инструмент для оператора**, а не публичный продукт. Поэтому:

- **Backend:** те же FastAPI `api/v1` (JSON) — панель их только потребляет.
- **Frontend по умолчанию:** серверный рендер + **HTMX** (быстро строится, не требует
  отдельного фронтенд-пайплайна, достаточно для ops). API остаётся чистым JSON, поэтому
  **SPA (React/Vue) можно добавить позже** без переписывания бэкенда.

> Это осознанный выбор «доставить быстро»: для одного-двух операторов SPA — избыточная сложность.
> Если появится команда операторов с богатым UX — переключение на SPA не ломает API.

## ⚠️ Аналитика: показываем только то, что реально есть (следствие Части 7)

Bot API **не отдаёт** просмотры и реакции постов канала. Значит дашборд **не имеет права**
рисовать `просмотры/ER/CTR` как достоверные. Разводим:

| Метрика | Доступность на Bot API | Источник |
|---|---|---|
| Рост подписчиков | ✅ | `getChatMemberCount` (снимки во времени) |
| Успех/сбой публикаций, размер очереди, ретраи | ✅ | внутренние `tasks`/логи |
| Расходы API (токены, стоимость) | ✅ | `api_usage`/`image_usage` (Часть 4) |
| Клики по трекинг-ссылкам | ✅ (если ссылки размечены) | внешний редирект/UTM |
| **Просмотры поста, ER, CTR, реакции** | ❌ **недоступно** | требует **MTProto stats-адаптера** или Telegram channel `stats` (только крупным каналам) |

**Правило панели:** недоступные метрики либо скрыты, либо явно помечены «требует MTProto-адаптера
статистики», но **не** показываются выдуманными нулями/оценками. Это же ограничивает сигнал
обучения (bandit, Часть 5) — до адаптера он опирается на рост подписчиков и клики.

## AUTHENTICATION

Защищённый вход · MFA (при необходимости) · управление сессиями · журнал входов · принудительное
завершение сессий. **Секреты (API-ключи, токены) — только write-only поля**, никогда не
отображаются в открытом виде (Часть 13); хранятся в env/секрет-хранилище, не в БД plaintext.

## USER ROLES — согласование с Частью 4

Черновик вводит 5 ролей, в Части 4 их 3 (`owner/admin/viewer`). **Расширяем enum** до:

| Роль | Доступ |
|---|---|
| **owner** | полный, включая критические настройки безопасности |
| **admin** | управление системой, кроме критической безопасности |
| **editor** | только контент (создание/правка/утверждение) |
| **analyst** | только статистика |
| **viewer** | только просмотр |

> Расширение `role` enum — миграция (Часть 4). Права проверяются на уровне `api`/`services`
> (RBAC), не только в UI — UI-скрытие не является защитой.

## DASHBOARD (главная)

Каналы · публикации сегодня · ошибки · задачи · очередь · **API-расходы** · статус моделей ·
статус Telegram · память · диск · статус backup · последние события. Реалтайм — поллинг
метрик-эндпоинта (не пушим без нужды).

## CHANNEL MANAGEMENT / SETTINGS

Создать · отключить (`paused`) · **удалить логически** (soft, Часть 4) · редактировать ·
клонировать · экспорт/импорт. Настройки: стиль, язык, LLM, Image Provider, расписание, эмодзи,
CTA, тон, правила, ограничения (пишутся в профиль канала — источник истины в БД, Часть 3).

## PERSONA MANAGER

Создать/изменить/архивировать/назначить каналу; биография, стиль, характер, словарь, референсы
(`personas`, Часть 4). Persona = текстовый голос (Часть 4/9).

## IMAGE MANAGER

Просмотр/удаление/архив/**перегенерация** (= задача `generate_image`)/история/промпты/negative/
похожесть (phash+CLIP, Часть 6).

## CONTENT MANAGER

Создать пост вручную · отправить в AI (= `generate_text`) · редактировать · утвердить/отклонить
(approval) · перегенерировать · запланировать (ставит слот в `schedules`/задачу с `run_at`) ·
сохранить как шаблон.

## KNOWLEDGE MANAGER

Загрузить/удалить/обновить документ · история версий · переиндексация · назначить каналу.
Работает с `documents`/`document_chunks` (**аддендум Части 9**).

## PROMPT MANAGER

Редактирование промптов: System · Image · Negative · Sales · Story · Morning · Evening…
Хранятся в `prompts` с версиями (Часть 4); правка = новая версия, не перезапись.

## SCHEDULER MANAGER / TASK MONITOR

Очередь: просмотр · стоп · ручной запуск · правка расписания · повтор · удаление. Статусы —
**канонические из Части 8** (`pending/running/deferred/succeeded/failed/needs_review/cancelled/dead`),
плюс время выполнения, причина ошибки, число попыток. DLQ (`dead`) — с ручным requeue.

## LOG VIEWER

Ошибки/предупреждения/события/API/Telegram/LLM-запросы + поиск/фильтр/экспорт. Секреты в логах
маскированы (Часть 13).

## ANALYTICS DASHBOARD

Показывает **только доступное** (см. таблицу выше): рост каналов, динамику публикаций, расходы,
эффективность CTA/тем (по внутренним прокси-метрикам), эффективность моделей. Просмотры/ER/CTR —
только при подключённом MTProto-адаптере, иначе помечены недоступными.

## COST DASHBOARD

Расход OpenAI/Anthropic/генерации изображений/эмбеддингов · общая стоимость · по каналам/дням/
моделям. Источник — `api_usage`/`image_usage`. **Ключевой раздел** для масштаба (Часть 2:
стоимость — реальный потолок).

## HEALTH DASHBOARD

Состояние: PostgreSQL · Redis · LLM · Telegram · Storage · Scheduler · Workers · Memory · Queue.
Питается `health_check`-задачами (Часть 8).

## SEARCH / BULK ACTIONS / EXPORT / IMPORT

- **Search:** посты/каналы/актёры/промпты/изображения/ошибки/логи/документы (гибрид, Часть 9).
- **Bulk:** массовая публикация/настройка/перегенерация/архив/экспорт/удаление.
  > **Флаг:** массовая публикация **уважает пер-бот лимиты Telegram** (Часть 7) — ставит задачи
  > в очередь с rate-limit, не fire-and-forget; массовое «удаление» — soft.
- **Export/Import:** контент, аналитика, логи, изображения, KB, конфиги, история, каналы,
  персоны, шаблоны. Импорт каналов = seed-формат (Часть 3).

## API MANAGEMENT

Управление ключами/лимитами/провайдерами/квотами/статусами. Ключи — write-only, в
секрет-хранилище (Часть 13).

---

## ⚠️ Аддендум к Части 4: audit & config versioning

SECURITY/VERSION CONTROL черновика требуют таблиц, которых в схеме нет:

- **`audit_log`** — `actor_user_id`, `action`, `entity`, `entity_id`, `before jsonb`,
  `after jsonb`, `created_at`. Все действия панели аудируются.
- **`config_versions`** — версии конфигурации: `author`, `date`, `description`, `snapshot jsonb`,
  для сравнения и **отката**.

Без них «аудит всех действий» и «откат конфигурации» не реализуемы. Сводится в Часть 4 при
финальной сборке.

## NOTIFICATION CENTER

Единый центр: ошибки, предупреждения, завершённые задачи, неудачные публикации, новые backup,
критические события. Дублирует внешние каналы уведомлений (Notification-модуль, Часть 2).

## VERSION CONTROL / SECURITY

Аудит всех действий · фиксация изменений конфигурации · откат · RBAC. Реализуется через
`audit_log`/`config_versions` выше + проверки прав в `services`.

## FUTURE EXTENSIBILITY / UX

Новые разделы — через единый механизм регистрации, без переработки. UX: быстрый, понятный,
адаптивный, единообразный, ориентированный на **много каналов** — приоритет скорости управления
и минимума действий на типовую операцию.

## AI STUDIO (твоё дополнение — sandbox)

Рабочее пространство для развития системы **без риска для живых каналов**:

- тест новых промптов · сравнение ответов разных LLM · генерация **без публикации** (dry-run) ·
  проверка качества изображений · измерение стоимости · анализ влияния изменений.

> **Изоляция обязательна:** AI Studio **не пишет в память каналов и не публикует** — работает в
> режиме draft/dry-run, чтобы эксперименты не отравляли Content/Style Memory и не улетали в Telegram.

## Reconciliation

- Панель = клиент `services`/`api`, ручные операции идут через ту же очередь (один код-путь).
- Аналитика показывает **только доступное на Bot API**; просмотры/ER/CTR — за MTProto-адаптером.
- Роли расширены до 5 (`owner/admin/editor/analyst/viewer`) — миграция enum; RBAC на бэкенде.
- **Аддендум Части 4:** `audit_log`, `config_versions` (аудит и откат).
- Bulk-публикация уважает лимиты Telegram; удаление — soft.
- AI Studio изолирован: без записи в память и без публикации.
- Frontend: HTMX-over-FastAPI по умолчанию, SPA — опционально позже.
