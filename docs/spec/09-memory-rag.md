## GLOBAL OBJECTIVE

Долговременная память: хранит знания, примеры, историю, особенности каждого канала и отдаёт AI
**только то, что нужно для текущей задачи** — без раздувания контекста.

## MAIN RESPONSIBILITIES

Память по каналу · примеры публикаций · профили персон · знания · векторный поиск · поиск
похожих · предотвращение повторов · сборка контекста · обновление памяти после публикации.

## MEMORY LEVELS

| Уровень | Где хранится | Изоляция |
|---|---|---|
| **1. Global** | правила/стандарты системы | общий (единственный кросс-канальный) |
| **2. Channel** | стиль, лексика, темы, структура, CTA, ритм | по `channel_id` |
| **3. Persona** | биография, манера, выражения, характер, ценности, истории | `personas` (Часть 4) |
| **4. Content** | все опубликованные посты | `memory` kind=`published_post` |
| **5. Image** | локации, одежда, композиции, позы, ракурсы, эмоции | `images` (метаданные, Часть 4/6) |
| **6. Analytics** | успешность публикаций | `analytics_snapshots` |

> **Флаг из Части 7:** уровень 6 (Analytics Memory) на чистом Bot API беден — views/ER постов
> недоступны. Сигнал обучения (Часть 5, bandit) ограничен ростом подписчиков и кликами по
> ссылкам, пока не введён MTProto-адаптер чтения статистики. Это не проблема Memory Engine, но
> определяет, чем он реально наполнится.

## ⚠️ Пробел схемы: Knowledge Base требует таблиц, которых нет в Части 4

База знаний (правила, документы, FAQ, гайды) — это **не** `memory` (память пользователя/канала).
Ей нужны собственные таблицы с версионированием. **Аддендум к Части 4:**

- **`documents`** — `id`, `source`, `author`, `doc_type`, `language`, `channel_id` (nullable —
  общие/канальные), `persona_id` (nullable), `active_version`, `tags text[]`, базовые колонки.
- **`document_chunks`** — `id`, `document_id FK`, `version`, `chunk_index`, `text`,
  `embedding vector(N)` (та же платформенная размерность), `metadata jsonb`. HNSW на `embedding`.

Knowledge Base ≠ Content Memory: первая — справочные знания, вторая — история постов. Не смешивать.

## DOCUMENT INGESTION

Загрузка документа: проверка формата → извлечение текста → очистка → **семантическое
разбиение** → эмбеддинги → индексация → сохранение метаданных.

> Ingestion — **прямой вызов, не задача очереди** (не плодим `task_type` и enum-миграции,
> принцип из Части 2).

### CHUNKING STRATEGY

Резать по **смысловым блокам**, не строго по символам. Ориентир: целевой размер чанка под окно
embedding-модели (напр. 200–500 токенов) с небольшим перекрытием, границы — по абзацам/предложениям.
Чанкинг — **чистая логика, покрывается юнит-тестами** (без сети/БД).

### METADATA (на чанк)

uuid · источник · автор · тип документа · дата · язык · теги · канал · персона · версия.

### EMBEDDINGS

Единый формат в пределах индекса (платформенная размерность, Часть 4). Смена модели →
**батч-переиндексация** всего корпуса (осознанная операция, не переключатель).

## VECTOR STORE

**pgvector** (Часть 4) — отдельное спец-хранилище не вводим без доказанной потребности. Поиск:
ближайшие соседи (HNSW) · фильтр по метаданным · **только внутри канала** · по типу документа.

## RETRIEVAL PIPELINE

Определение задачи → формирование запроса → поиск релевантных → ранжирование → сборка контекста
→ передача в AI Engine.

## RERANKING — hard filter ≠ soft rank

Черновик ставит «совпадение канала» в список ранжирования. **Это ошибка уровня безопасности:**
канал — не релевантность, а **изоляция**. Разводим (как hard-gate/soft-score в Части 5):

**Hard filters (WHERE, до ранжирования — обязательны):**

- `channel_id` (кроме Global Memory) — **security**, не опция;
- тип документа (если задан);
- только **активная версия** документа (кроме аудита).

**Soft ranking (ORDER, после фильтра):**

1. семантическая близость темы (вектор);
2. опциональный cross-encoder reranker;
3. свежесть;
4. доверие источнику.

Persona-скоуп — тоже hard filter, если задан. Кросс-канальные данные при генерации **запрещены**,
кроме явной настройки (Часть 13).

## CONTEXT ASSEMBLY

Собирается автоматически и **компактно** (≤ `MAX_CONTEXT_TOKENS`, Часть 5): профиль канала +
персона + релевантные знания + успешные примеры + **последние публикации в разумном K (3–5,
не 500!)** + ограничения + инструкция задачи.

> Разведение из Части 5: **500 = окно векторного сравнения** (уникальность, ноль токенов);
> **в промпт идёт few-shot K=3–5**. Memory Engine обслуживает оба режима, но не путает их.

## MEMORY UPDATE (после успешной публикации)

Пост сохранён → эмбеддинг создан → память канала обновлена → статистика тем → история CTA →
история изображений. Пишется в рамках закрытия задачи `collect_metrics`/`publish` транзакционно.

## MEMORY RETENTION

Тиры: **active** (горячее, в HNSW) · **archive** (холодное, но искомое) · **purge** (временные
служебные данные). Опубликованные материалы и важные знания — всегда искомы (soft delete, Часть 4).

> **Флаг масштаба:** retention — не только про диск. На «миллионах векторов» HNSW деградирует;
> вынос старых низкоценных векторов из активного индекса держит поиск быстрым. Это часть
> производительности, а не уборка.

## DUPLICATE PREVENTION

Перед генерацией AI получает самые похожие публикации; при чрезмерной близости — сменить угол/
структуру/историю/CTA, при необходимости — тему (порог `similarity_threshold`, Часть 1/5).

## STYLE EVOLUTION

Стиль развивается **плавно**: адаптация словаря с учётом успешности новых приёмов, без потери
узнаваемости. Управляется медленным обновлением (bandit, Часть 5) — не скачками.

## KNOWLEDGE VERSIONING

Документы версионируются: при обновлении — старая версия сохраняется, новая индексируется,
активная помечается (`documents.active_version`). Retrieval берёт только активную (аудит — все).
Обеспечивает воспроизводимость.

## SEARCH MODES — гибрид конкретно

Семантический (вектор) · по ключевым словам (FTS/`pg_trgm`, Часть 4) · **гибридный** (слияние,
напр. Reciprocal Rank Fusion) · только по типу документа.

## SECURITY

Память каналов **полностью изолирована** — каждый векторный запрос содержит `WHERE channel_id`
(кроме Global). Данные одного канала при генерации для другого — запрещены без явной настройки
(Часть 13).

## OBSERVABILITY (на каждый запрос)

Время поиска · сколько найдено · сколько использовано · длительность сборки контекста · итоговый
объём контекста (токены). Пишется для контроля стоимости и раздувания промпта.

## STYLE MEMORY (твоё дополнение — как отдельный слой)

Хранит **не тексты, а абстрактные признаки стиля** на канал/персону:

- распределение длины предложений;
- частота диалогов;
- структура абзацев;
- эмоциональная динамика (арка поста);
- характерные речевые обороты;
- способы переходов между мыслями.

Формат: структурированный `jsonb` (+ опционально style-эмбеддинг). Промпт-билдер инжектит
**параметры стиля**, а не старые посты → стиль воспроизводится точнее и **без буквального
копирования** (синергия с duplicate prevention).

> **Честная оговорка:** извлечение этих признаков (особенно «эмоциональная динамика» и «переходы»)
> — само по себе отдельная NLP-задача со своим экстрактором и валидацией; это не бесплатное
> производное от текста. На старте наполняем измеримыми признаками (длины, частоты, обороты),
> сложные (арка/переходы) — по мере готовности экстрактора.

## FUTURE EXTENSIBILITY

Заложить (без спекулятивной реализации): авто-извлечение знаний из публикаций, поиск по
изображениям, мультимодальные эмбеддинги, аудио/видео-источники, объединение дублей знаний.

## Reconciliation

- KB требует новых таблиц (`documents`, `document_chunks`) — **аддендум к Части 4**.
- Изоляция канала = **hard filter** (security), не вес реранкинга.
- Few-shot в промпт = K 3–5; 500 — окно сравнения (Часть 5), не контент промпта.
- Analytics Memory ограничена лимитом Bot API (Часть 7).
- Style Memory = признаки, не тексты; сложные признаки — по готовности экстрактора.
- Retention влияет на скорость HNSW, не только на диск.
