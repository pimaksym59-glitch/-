# Часть 8. Scheduler & Automation Engine

> Заполняет пробел между [Частью 7](07-telegram-engine.md) и [Частью 9](09-memory-rag.md).
> Опирается на очередь `tasks` и enum'ы из [Части 4](04-database-design.md), пайплайн из
> [Части 2](02-architecture.md)/[5](05-ai-engine.md), политику ретраев из [Части 1](01-system-prompt.md).

## GLOBAL OBJECTIVE

Центральный координатор: **не создаёт контент и не публикует**, а управляет временем запуска,
очередями, зависимостями и периодическими сценариями. Работает 24/7, переживает перезапуск
(состояние — в Postgres, не в памяти процесса).

## Два процесса (ключевое разграничение)

Scheduler — это **продюсер**, воркеры — **исполнители**. Ровно как в Части 3:

- **Scheduler-процесс** (`scheduler/run.py`): материализует задачи из `schedules` и запускает
  периодические сценарии → кладёт строки в `tasks` с `run_at`. **Никакой бизнес-логики.**
- **Worker-процессы** (`workers/run.py`): разбирают очередь `FOR UPDATE SKIP LOCKED`, исполняют
  обработчик по `task_type`, на успехе ставят следующую стадию.

---

## Согласование типов и статусов задач с Частью 4

Черновик ввёл имена (`GenerateContent`, `PublishPost`…), расходящиеся с enum'ом Части 4.
**Канонический набор — один** (snake_case), каждый лишний тип = enum-миграция (принцип Части 2):

| Канон (`task_type`) | Черновик |
|---|---|
| `generate_text` | GenerateContent |
| `validate` | ValidateContent |
| `generate_image` | GenerateImage |
| `publish` | PublishPost |
| `collect_metrics` | UpdateAnalytics |
| `backup` | BackupDatabase / BackupImages (параметр в payload) |
| `cleanup` | CleanupStorage |
| `reindex` | RebuildEmbeddings / RefreshKnowledgeBase |
| `health_check` | HealthCheck |

**Статусы** (`task_status`, дополняем Часть 4 + Часть 7):
`pending` (Queued) · `running` · `succeeded` · `failed` · `deferred` (Retry Scheduled / вне окна) ·
`needs_review` (Часть 7) · `cancelled` · `dead` (DLQ). Расширение enum — осознанная миграция.

### TASK LIFECYCLE

```
created → pending → running → succeeded
                       ↓
                     failed → (attempts<MAX) deferred → pending
                       ↓ (attempts=MAX)
                     dead (DLQ)
created → cancelled
```

## DEPENDENCY MANAGEMENT — это continuation-chaining, НЕ DAG-движок

Черновик рисует цепочку зависимостей. Не строим отдельный движок зависимостей — Части 2/5 уже
задали механику: **каждый обработчик на успехе ставит следующую стадию**.

```
generate_text →(ok)→ validate →(ok)→ generate_image →(ok)→ publish →(ok)→ collect_metrics
```

- сбой стадии → цепочка **не продолжается** (следующая не ставится), задача уходит в
  retry/dead по политике;
- это проще и надёжнее DAG для **линейного** пайплайна;
- полноценный DAG (`depends_on`, fan-in/fan-out) вводим **только** если появится реальное
  ветвление — не спекулятивно.

---

## LEAD TIME — то, без чего «отложенный постинг» не работает

Пост на 08:00 нельзя начать генерировать в 08:00 — текст+изображение+возможные переписывания
занимают время. **Слот в `schedules` = время публикации; генерация ставится заранее:**

- `generate_text.run_at = slot_time − LEAD_TIME` (деф. напр. 30–60 мин, конфигурируемо);
- цепочка стадий исполняется в пределах lead time;
- `publish.run_at = slot_time` (ровно слот — Telegram сам не планирует, Часть 7);
- если генерация не уложилась в lead time → публикация деферится на ближайшее валидное окно,
  а не выходит за рамки (см. Publication Windows).

Это связывает Часть 6 (сцена по времени суток — берётся из `slot_time`) и Часть 7 (наша очередь держит `run_at`).

## SCHEDULING MODES

Одноразовый · ежедневный · еженедельный · ежемесячный · по интервалу · по событию · вручную.
Хранится в `schedules` (Часть 4) как cron/правило; scheduler разворачивает в конкретные `run_at`.

## TIMEZONE SUPPORT

Время хранится в **UTC**, расчёт слота — в **локальном tz канала** (IANA), преобразование при
планировании/отображении. Использовать корректную tz-библиотеку.

> **Флаг DST:** на переходе на летнее/зимнее время слот может не существовать (пропуск часа) или
> случиться дважды. Правило разрешения фиксируется (напр. «несуществующее → сдвиг вперёд»,
> «двойное → первое вхождение»), иначе — пропуск или дубль публикации.

## PUBLICATION WINDOWS

На канал — допустимые окна (утро/день/вечер). Задача вне окна → **deferred** на ближайшее
валидное время, не отбрасывается.

## PRIORITY QUEUE

`critical/high/normal/low` — колонка `priority`; разбор `ORDER BY priority, run_at`. Срочные
обходят обычные. Справедливость между каналами (Часть 7) — чтобы приоритетный бэклог одного не
голодал остальные.

---

## PARALLEL EXECUTION + CONCURRENCY LIMITS

Независимые задачи (разные каналы, backup, аналитика) — параллельно разными воркерами. Но с
**лимитами**, иначе выбьем внешние API (узкое место масштаба, Часть 2):

- на `task_type`: напр. не более N одновременных `generate_image`;
- на провайдера: не более M одновременных вызовов конкретной LLM / генератора изображений;
- на публикации: пер-бот лимит Telegram (Часть 7).

Реализация — ограниченные пулы воркеров + **семафор/token-bucket по ключу провайдера** (общий
rate-limiter из Части 2). Это и есть защита от 429.

## RETRY STRATEGY

`MAX_RETRIES` + экспоненциальный backoff с джиттером (Часть 1). Транзиентные — ретрай;
перманентные (конфиг/права/авторизация) — сразу в `needs_review`/владельцу без ретрая (Часть 7).
Параметры конфигурируемы.

## DEAD LETTER QUEUE

Исчерпан `MAX_RETRIES` → задача в `dead`: сохраняется причина (`last_error`), уведомление
владельцу, **ручной requeue** после устранения причины. DLQ — не отдельная таблица, а статус +
фильтр (проще, одна очередь).

---

## Мульти-инстанс scheduler без дублей

Черновик требует масштабирования и «одна задача не исполняется дважды». Разделяем два риска:

- **Дубль исполнения** воркерами — уже решён `FOR UPDATE SKIP LOCKED` (Часть 4): сколько угодно воркеров безопасны.
- **Дубль материализации** — если N scheduler-инстансов создадут один слот дважды. Решение:
  **идемпотентный ключ слота** — `UNIQUE(channel_id, schedule_id, slot_datetime)` (partial, Часть 4):
  повторная вставка того же слота отклоняется БД. Дополнительно — `pg_advisory_lock` на цикл
  материализации (только один инстанс планирует за раз). Leader election не обязателен.

## AUTOMATION SCENARIOS (конфигурируемые)

Ежедневная генерация · еженедельная очистка кэша · ежедневный backup · ежемесячный reindex ·
регулярная переиндексация KB. Каждый — периодическая задача канонического типа.

## HOLIDAY SUPPORT

Календарь событий на канал (гос./религиозные праздники, сезонные кампании). При наличии правила
scheduler **не пишет контент**, а выбирает соответствующий **контент-план**, который меняет
выбор темы в Части 5. Scheduler только координирует, генерирует — AI Engine.

## HEALTH CHECKS (периодически)

БД · очередь · LLM-провайдеры · генераторы изображений · Telegram-интеграция · свободное место.
Проблема → уведомление + запись в журнал. Питает мониторинг (Часть 10).

## MAINTENANCE TASKS

Очистка temp · устаревший кэш · `VACUUM/ANALYZE` · проверка целостности · обновление статистики.
Как `cleanup`/`reindex` задачи.

## OBSERVABILITY

На задачу: id · created/started/finished · длительность · статус · число ретраев · журнал
выполнения (Часть 4 + логи Части 2). Для диагностики и аудита.

## PAUSE & RESUME

Пауза отдельной задачи · паузa канала (`channel.status=paused`) · остановка типа задач ·
безопасное возобновление **без потери очереди** (состояние в Postgres, не в памяти).

## SCALABILITY / EXTENSIBILITY

Несколько инстансов scheduler (идемпотентность выше) и произвольное число воркеров. Новый тип
задачи = новый обработчик, зарегистрированный в **едином реестре** (`scheduler.registry`,
Часть 3) + enum-миграция; становится доступен системе без правки существующих обработчиков.

## DESIGN PRINCIPLES

Scheduler **не содержит** логики генерации/публикации — только координация, планирование и
жизненный цикл задач. Специализированные действия — в соответствующих модулях.

---

## Reconciliation

- Типы/статусы задач сведены к **каноническому enum** Части 4 (+`needs_review`, `cancelled`, `dead`).
- «Зависимости» = continuation-chaining (каждая стадия ставит следующую), не DAG-движок.
- Введён **LEAD_TIME**: генерация ставится до слота, `publish` — на слот (иначе отложенный постинг не работает).
- Concurrency/rate-limit — семафор по провайдеру (общий лимитер Части 2), защита от 429.
- Мульти-инстанс: воркеры — SKIP LOCKED; продюсер — идемпотентный ключ слота + advisory lock.
- DLQ = статус `dead`, не отдельная таблица.
