# Часть 7. Telegram Engine

## GLOBAL OBJECTIVE

Исполнительный модуль: безопасная, надёжная, полностью автоматическая публикация. AI решает —
Telegram Engine выполняет.

---

## Решение: Bot API (aiogram), не MTProto

Черновик оставляет «способ публикации» открытым. Фиксируем:

**Основной транспорт — Telegram Bot API через aiogram.** MTProto (Pyrogram/Telethon) — только
как опциональный адаптер за тем же интерфейсом, при конкретной доказанной потребности.

**Почему Bot API:**

- официально разрешённая автоматизация; постинг user-аккаунтами через MTProto **нарушает ToS и
  ведёт к банам** — для продукта «вести каналы 24/7» это неприемлемый риск;
- покрывает всё нужное: текст, фото, альбом (media group), видео, edit, delete, pin, опросы;
- условие: **бот должен быть админом канала** (с правом постинга) — это часть заведения канала.

**Ограничения Bot API, которые меняют дизайн (ниже разобраны):** нет серверного планирования,
нет чтения просмотров/реакций постов, публикация at-least-once.

---

## ⚠️ Ограничение 1: нет серверного отложенного постинга

Bot API **не умеет** «опубликовать в 08:00» на стороне Telegram (это фича нативных
клиентов/MTProto). Значит:

> **Планирование держит НАША очередь** (Часть 8): задача `publish` лежит с `run_at`, воркер
> берёт её в нужный момент и шлёт **немедленно**. Не полагаемся на Telegram в вопросе времени.

## ⚠️ Ограничение 2: нет просмотров и реакций постов канала

Bot API **не отдаёт** количество просмотров поста канала и счётчики реакций. Это подрывает
метрики Части 10 (views / ER / CTR по постам).

> **Следствие для Части 10:** «просмотры/ER/CTR по постам» через Bot API **недоступны**.
> Варианты: (а) MTProto-адаптер только для чтения статистики (сам постинг остаётся на Bot API);
> (б) Telegram channel `stats` (доступны только крупным каналам, через MTProto); (в) считать
> только то, что доступно (рост подписчиков через `getChatMemberCount`, клики по трекинг-ссылкам).
> Это решается в Части 10, но флагуется здесь как реальность транспорта.

## ⚠️ Ограничение 3: публикация at-least-once → идемпотентность

Если запрос на отправку ушёл, а ответ (с `message_id`) не дошёл (таймаут) — неизвестно,
опубликовалось ли. Слепой ретрай = **двойной постинг**. Бот при этом **не может** прочитать
историю канала, чтобы проверить.

**Правило:**

- перед отправкой фиксируем намерение с `dedup_key` (Часть 4);
- при **однозначном** сбое до отправки (сеть/подготовка) — ретрай по политике;
- при **неоднозначном** исходе (запрос ушёл, ответа нет) — задача в статус `needs_review`,
  **без авто-ретрая**; владелец решает. Лучше отложить, чем опубликовать дважды.

## PUBLISHING PIPELINE

```
receive approved content → validate channel settings → check schedule/run_at →
prepare media → upload media → publish (немедленно) → verify success →
save message_id (транзакционно с задачей) → enqueue collect_metrics → notify system
```

## CHANNEL CONFIGURATION

Telegram channel id · username · режим публикации · язык · часовой пояс · формат сообщений ·
разрешённые типы медиа · правила оформления · **режимы draft/approval** (см. ниже).

## PUBLISHING MODES

Только текст · текст+фото · текст+несколько фото · текст+видео · альбом (media group) ·
документ · голосовое (если поддержится). Режим — из настроек канала.

## MESSAGE FORMATTER

Перед отправкой: Markdown/HTML (лучше **MarkdownV2/HTML с экранированием** — у Telegram строгие
правила спецсимволов), переносы, длина (текст ≤4096; **подпись медиа ≤1024** — отдельный лимит!),
ссылки, эмодзи, спецсимволы. Нарушение лимитов — это rule-based gate ещё в `validate` (Часть 5).

## MEDIA MANAGER

Загрузка изображений/видео · временное хранение · повторная отправка при сбоях · очистка temp.
Крупные медиа — по `file_id` после первой загрузки (переиспользование без повторного upload).

## ALBUM SUPPORT

Media group 1–10 элементов; подпись — по настройкам канала (в Telegram подпись альбома крепится
к первому элементу).

---

## DELAYED PUBLISHING

Немедленные · запланированные (через `run_at` нашей очереди, см. Огр.1) · перенесённые ·
повторные после ошибки.

## RETRY POLICY — согласование с Частью 1

Не собственная лесенка «3 попытки», а **`MAX_RETRIES=5` + backoff** из Части 1, с уточнениями:

- **429 → honor `retry_after`** из ответа Telegram **точно** (перекрывает обычный backoff);
- **перманентные ошибки** (bad token, chat not found, bot kicked, no rights) — **без ретрая**,
  сразу владельцу;
- **транзиентные** (сеть, 5xx) — ретрай с backoff;
- исчерпан лимит → уведомление владельца + задача в очередь ошибок.

## RATE LIMIT HANDLING — конкретика

Лимиты Telegram **пер-бот**: ~30 сообщений/сек суммарно, к одному чату — ~1 сообщение/сек
устойчиво (всплески ловят 429). При 429 — пауза на `retry_after`, задача сохраняется, продолжаем
после. Реализуется общим rate-limiter'ом (Часть 2), ключ — `bot_token` + `channel_id`.

> **Флаг масштаба:** лимиты **пер-бот** → 1000 каналов на одном боте упрутся в общий потолок
> 30/сек. Поэтому при росте — **отдельный bot-токен на канал (или группу каналов)**, чтобы
> лимиты масштабировались. Один бот на всё — только для малого числа каналов.

## MESSAGE HISTORY

Сохранять: `message_id` · дата · канал · текст · медиа · статус · результат. Пишется
транзакционно с закрытием задачи `publish` (иначе рассинхрон при сбое).

## EDIT / DELETE / PIN

- **Edit:** взять `message_id` → `editMessageText` / `editMessageMedia` (медиа-сообщения) →
  сохранить новую версию в `post_history`.
- **Delete:** только после проверки прав и записи в журнал; история удаления сохраняется
  (soft, Часть 4). Физическое удаление в Telegram необратимо — фиксируем событие.
- **Pin:** закрепить/открепить/заменить/авто-открепить по таймеру (если настроено).

## COMMENT SUPPORT

При связанной группе обсуждений: сохранять ссылку на обсуждение; чтение новых комментариев
**возможно только если бот в группе обсуждения** (иначе недоступно) → в Analytics передаём то,
что реально доступно.

---

## MULTI-CHANNEL QUEUE (логически, физически — одна таблица)

«Своя очередь на канал» реализуется **не N физическими очередями**, а одной таблицей `tasks`
(Часть 4) с честным разбором: `WHERE channel_id=...` + справедливость в `SKIP LOCKED`-выборке,
чтобы бэклог одного канала **не голодал** остальные. Недоступность одного канала не блокирует
другие (его задачи деферятся, воркер идёт дальше).

## PRIORITY SYSTEM

Приоритеты `critical/high/normal/low` — колонка `priority` в `tasks`; срочные обходят обычные в
выборке `ORDER BY priority, run_at`.

## DRAFT MODE / APPROVAL MODE

Флаги канала:

- **Draft:** текст+изображение создаются, `publish` **не** выполняется, материал сохраняется на ручную проверку.
- **Approval:** пайплайн **останавливается перед `publish`**, владелец получает уведомление и
  выбирает: опубликовать / отклонить / на регенерацию. Переиспользует механизм ревью из Частей 5–6.

## PUBLICATION RULES (перед отправкой)

Корректность текста · наличие обязательных медиа · соответствие расписанию · статус канала
(`active`) · **отсутствие дублирующей публикации** (`dedup_key`).

---

## ERROR CATEGORIES

Сеть · авторизация · Telegram API · медиа · форматирование · конфигурация · внутренние.
Разделение важно для ретрая: сеть/5xx/429 — транзиентные (ретрай); авторизация/конфиг/права —
перманентные (сразу владельцу, см. Retry Policy).

## LOGGING / MONITORING

Лог на публикацию: начало/окончание · канал · тип · размер текста · число медиа · результат ·
длительность · ошибки. Метрики мониторинга: успешные публикации · ошибки · среднее время ·
число ретраев · размер очереди · активность по каналам.

## SECURITY

Токены Telegram — только через env/конфиг, никогда в коде и логах (маскирование). Минимум прав
у бота, регулярная сверка. При per-channel токенах — изоляция blast radius.

## FUTURE FEATURES

Заложить (не реализуя спекулятивно): мультиплатформенная публикация, адаптация текста под
платформы, A/B-тесты, умное распределение времени, внешняя аналитика, новые типы контента —
через тот же интерфейс.

---

## Reconciliation

- Транспорт — **Bot API/aiogram**; MTProto только опциональный адаптер (и, возможно, чтение статистики).
- Планирование времени — **наша очередь** (`run_at`), не Telegram.
- Просмотры/реакции постов через Bot API **недоступны** → влияет на Часть 10.
- Публикация at-least-once → неоднозначный сбой = `needs_review`, не авто-ретрай.
- Ретраи — `MAX_RETRIES`+backoff (Часть 1), 429 honors `retry_after`; перманентные ошибки без ретрая.
- Лимиты пер-бот → при масштабе токен на канал/группу.
- «Очередь на канал» — логическая (одна `tasks` + справедливый SKIP LOCKED), не физическая.
