# Часть 2. Архитектура проекта

> Продолжает [Часть 1](01-system-prompt.md). Числовые контракты (ретраи, backoff, пороги
> уникальности) заданы там и здесь не переопределяются — только ссылаются.

## GLOBAL OBJECTIVE

Система полностью автоматизирует ведение любого количества Telegram-каналов, работает 24/7,
каждый компонент независим, любой воркер перезапускается без остановки остальных, масштабирование
горизонтальное.

---

## ARCHITECTURE STYLE — ключевое решение

Черновик называет 10 «сервисов». Важно зафиксировать, что это значит физически, потому что от
этого зависит вся Часть 3.

**Решение: модульный монолит с общей очередью задач и горизонтально масштабируемыми воркерами.**
Не 10 отдельных сетевых микросервисов.

**Почему именно так (а не микросервисы):**

- «Database Service» и «Memory Service» как отдельные сетевые сервисы — это оверинжиниринг:
  они всё равно ходят в одну PostgreSQL. Сетевая граница между ними даёт латентность и точки
  отказа, но не даёт независимости.
- Независимость перезапуска и горизонтальное масштабирование достигаются **процессами-воркерами
  поверх общей очереди** (Postgres как source of truth, `FOR UPDATE SKIP LOCKED`), а не
  разрезанием кода по HTTP-границам.
- Замена провайдера (Часть, «EXTENSIBILITY») требует не микросервиса, а **чистой абстракции
  внутри модуля** — интерфейс + реализации + фейк.

**Что это даёт на практике:**

- один код-базис, чёткие границы модулей (каждый «сервис» = пакет с публичным интерфейсом);
- масштабирование = запуск N экземпляров воркера (`docker compose up --scale worker=N`);
- отказ одного воркера не роняет остальные — задача возвращается в очередь;
- любой модуль тестируется изолированно через провайдер-абстракции с фейками (offline-режим).

Границы модулей остаются ровно такими, как в списке ниже — меняется только способ их запуска.
Если позже какой-то модуль реально упрётся в масштаб (например, Image Service по GPU), его
можно вынести в отдельный деплой без переписывания остальных — интерфейс уже изолирован.

### Правила стиля (без изменений)

Каждый модуль отвечает только за свою область. Никаких монолитных файлов. Никаких файлов по
3000 строк. Никакой бизнес-логики внутри роутеров.

## MODULES (зоны ответственности)

| Модуль | Отвечает за |
|---|---|
| **AI** | генерация текста, анализ качества, RAG-запросы, генерация промптов, проверка уникальности, анализ изображений, работа с LLM |
| **Content** | контент-план, поиск тем, черновики, подбор CTA/эмоций/структуры, история публикаций |
| **Image** | генерация изображений, генерация промптов, адаптеры провайдеров (Nano Banana / OpenAI Images / Flux / Ideogram), проверка похожести, история изображений |
| **Telegram** | отправка/редактирование/удаление сообщений, отложенные публикации, альбомы, опросы, закрепления, комментарии |
| **Scheduler** | расписание, очереди, ежедневные/еженедельные/праздничные задачи, часовые пояса, повторы |
| **Storage (Database)** | доступ к PostgreSQL, миграции, индексы (backup/restore — уровень инфраструктуры, см. Часть 12) |
| **Memory** | RAG, эмбеддинги, векторный поиск (pgvector), история, примеры для few-shot |
| **Admin Panel** | просмотр/редактирование каналов, логи, мониторинг, ручная публикация, статистика |
| **Notification** | уведомления в Telegram/Discord/Email, ошибки, аварии |
| **Analytics** | просмотры, ER, CTR, рост, популярные темы, успешность публикаций |

> «Сервис» в тексте черновика = «модуль» здесь. Никакого смешения данных между каналами:
> любой запрос к любому модулю обязательно скоупится `channel_id`.

## DATA FLOW

```
Scheduler (по расписанию канала)
        │
        ▼
   Content ── запрашивает ──► AI ── запрашивает ──► Memory
        │                       │                      │
        │                       │   возвращает: последние посты, темы,
        │                       │   стиль, эмоции, запрещённые конструкции
        │                       ▼
        │                 AI пишет текст
        │                       │
        │                       ▼
        │                   Validator  (повторы, орфография, уникальность,
        │                       │        стиль, читабельность, эмоции)
        │                       ▼
        └───────────────►  Image  ── генерирует изображение
                                │
                                ▼
                        проверка похожести изображения
                                │
                                ▼
                          Telegram (публикация)
                                │
                                ▼
                          Analytics (сбор статистики)
```

Каждый новый день у канала начинается автоматически: Scheduler ставит задачу в очередь,
дальше пайплайн ведёт её по стадиям.

---

## PIPELINE (стадии одной публикации)

Каждый пост проходит один и тот же пайплайн. Каждая стадия — отдельный тип задачи в очереди,
идемпотентный, с сохранением промежуточного результата:

```
расписание → выбор темы → проверка памяти → поиск похожих →
создание текста → проверка текста → исправление →
промпт изображения → создание изображения → проверка изображения →
публикация → сохранение → обновление памяти → обновление статистики
```

Стадии `проверка текста → исправление` и `создание текста` образуют цикл переписывания,
ограниченный `MAX_REWRITES` (Часть 1). Публикация не наступает, пока валидатор не дал pass.

---

## MULTI CHANNEL

Каждый канал — отдельная независимая сущность со своими: настройками LLM, стилем, персонажами,
языком, эмоциями, CTA, расписанием, изображениями, темами, историей и памятью. Данные разных
каналов никогда не смешиваются — изоляция по `channel_id` на уровне каждого запроса к БД.

### CHANNEL PROFILE (что хранит канал)

`id` · название · описание · язык · ЦА · тематика · стиль · тон · счётчик публикаций ·
график · используемая модель · настройки генерации · персонажи · папка изображений · промпты ·
запрещённые темы · стоп-слова · любимые слова · типичные CTA · эмоциональный профиль.

> Полная схема профиля — в Части 4 (База данных). Пороги из Части 1 (`SIMILARITY_THRESHOLD`,
> `HUMANNESS_MIN`, окна) переопределяемы на уровне профиля канала.

---

## SCALABILITY

Система работает одинаково на 1 / 10 / 100 / 1000 каналов. Добавление канала не требует
изменения кода — только запись профиля.

**Честная оговорка:** узкое место при росте — не архитектура, а **лимиты и стоимость внешних
API** (Anthropic, OpenAI/провайдеры изображений, Telegram Bot API). Поэтому обязательны:

- горизонтальное масштабирование воркеров (компьют);
- **пер-провайдерный rate-limiter и контроль конкурентности** (чтобы N каналов не выбили
  общий лимит и не привели к 429);
- учёт стоимости на канал (см. LOGGING).

Без rate-limiting «1000 каналов» упрётся в 429, а не в CPU. Это фиксируется в Части 5/6.

---

## EXTENSIBILITY

Любой провайдер заменяется только внутри своего модуля через абстракцию «интерфейс + реализации
+ фейк». Пример: Nano Banana → Midjourney → Flux меняется исключительно в Image; остальной
проект не трогается. Аналогично для LLM и эмбеддингов.

---

## CONFIGURATION

Никаких настроек в коде. Источники: `.env` (секреты и инфраструктура) · база данных (профили
каналов, редактируемые из Admin Panel) · `config.yaml` (дефолты приложения). Приоритет:
БД (канал) > `.env` > `config.yaml` (дефолт).

---

## LOGGING

Логируется каждое действие: начало/окончание генерации, ошибки, запросы, ответы моделей, время
работы, **стоимость API**, размер текста, размер изображения, использованные токены. Логи
структурированные (JSON), с `channel_id` и `task_id` в каждой записи.

---

## ERROR HANDLING & FAIL SAFE

Любая ошибка: сохраняется → логируется → уходит владельцу → повторяется по политике
(`MAX_RETRIES`, backoff — Часть 1) → **не роняет систему** (задача возвращается в очередь,
воркер продолжает).

### AI FALLBACK (каскад)

1. Основная модель недоступна → **резервная модель** (другой tier/провайдер).
2. Резервная недоступна → **перенести публикацию** (reschedule).
3. Перенос невозможен → **уведомить владельца**.

Конкретные модели основного и резервного tier'а фиксируются в Части 5 (AI Engine).

---

## PERFORMANCE

Все тяжёлые задачи — асинхронно, через очередь. Публикация никогда не ждёт генерацию следующего
поста: стадии разных публикаций исполняются параллельно разными воркерами.

## CACHE (Redis)

Кэшируются: эмбеддинги, промпты, настройки, история, похожие посты, профили каналов. TTL и
ключи (`{channel_id}:...`) фиксируются в Части 4/9.

## BACKUP

Ежедневно автоматически: база, память (векторы), конфиги, изображения. Механика — Часть 12
(развёртывание), т.к. это инфраструктура, а не runtime-модуль.

## SECURITY

API-ключи только через переменные окружения. Секреты никогда не в коде и никогда в логах
(логгер маскирует поля-секреты). Подробно — Часть 13.
