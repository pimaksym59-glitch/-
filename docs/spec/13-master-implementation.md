# Часть 13. Master Implementation Specification

> Капстоун-документ. Сводит [Части 1–12](01-system-prompt.md) в единую систему, фиксирует

## GLOBAL MISSION

Production-ready AI-платформа, полностью автоматизирующая ведение любого числа Telegram-каналов:
сама генерирует контент и изображения, публикует, анализирует, хранит стиль каждого канала,
расширяется без изменения существующей архитектуры.

## ARCHITECTURE OVERVIEW (исправлено под Часть 2)

Черновик снова называет блоки «отдельными сервисами». **Это модули одного монолита** (решение
Части 2), исполняемые несколькими процессами поверх общей очереди — не микросервисы:

```text
Admin Panel (api-контейнер, HTMX) ──► services/api ──► БД (источник истины)
        │
Scheduler (продюсер) ──► Task Queue (Postgres, SKIP LOCKED) ──► Workers (×N исполнителей)
                                                                     │
   generate_text ─► validate ─► generate_image ─► publish ─► collect_metrics
        │              │              │              │             │
     AI Engine +   Validation     Image Engine   Telegram     Analytics +
     Memory/RAG     Engine                        Engine      Memory Update
```

Границы модулей = пакеты с публичными интерфейсами (Часть 3); «сервис» ≠ отдельный деплой.

## END-TO-END PIPELINE → 5 задач + chaining

19 этапов черновика группируются в **5 типов задач** (Часть 8), связанных continuation-chaining
(каждая на успехе ставит следующую), а не 19 отдельных задач:

| Задача | Этапы черновика | Модули |
|---|---|---|
| `generate_text` | 1–11 (расписание→тема→структура→черновик→стиль→уникальность→саморедактирование) | Scheduler ставит; AI + Memory/RAG |
| `validate` | (входит в 9–11 как gate) | Validation Engine |
| `generate_image` | 12–14 (промпт→генерация→проверка) | Image Engine |
| `publish` | 15–16 (финализация→публикация) | Telegram Engine |
| `collect_metrics` | 17–18 (статистика→обновление памяти) | Analytics + Memory |

Этап 1 (Scheduler) ставит `generate_text` на `slot − LEAD_TIME`; `publish` — на слот (Часть 8).
Сбой любой стадии → цепочка не продолжается, retry/DLQ по политике (Часть 1/8).

## IMPLEMENTATION ORDER

Строгий порядок (уточнён под очередь-как-backbone):

1. Структура репозитория → 2. Конфигурация (Pydantic Settings) → 3. Docker/Compose →
4. PostgreSQL (+pgvector) → 5. Redis → 6. Модели ORM → 7. Репозитории → 8. **Очередь `tasks` +
реестр обработчиков** → 9. Scheduler → 10. API → 11. Провайдер-абстракции (LLM/Image/Embed +
**фейки**) → 12. AI Engine → 13. Memory/RAG → 14. Validation → 15. Image Engine →
16. Telegram Engine → 17. Analytics → 18. Admin Panel → 19. Тесты (по ходу, не в конце) →
20. Документация.

> Сдвиг против черновика: **очередь и провайдер-фейки — раньше движков**, потому что вся система
> должна тестироваться offline (Часть 2). Тесты пишутся **вместе** с модулями, не отдельным
> финальным этапом.

## CODING RULES / STANDARDS

Каждый файл: одна ответственность · понятные имена · полная типизация · документация · единый
стиль · проходит статанализ · тесты где целесообразно. **Запрещено:** дублирование · циклические
зависимости · бизнес-логика в API · SQL в сервисах · секреты в коде · «магические» значения
вместо конфигурации (Часть 3).

## ABSTRACTIONS / VALIDATION GATE / OBSERVABILITY

- **LLM/Image/Embedding abstraction:** только слой интеграции знает провайдера; всё через единый
  интерфейс + фабрику + фейк (Часть 3/5/6).
- **Validation gate:** ни один пост без обязательных проверок (структура, язык, стиль,
  уникальность, соответствие каналу, успешная генерация изображения если требуется) — hard gates
  Части 5.
- **Observability:** каждый этап измерим (start/end/длительность/статус/ошибки/`task_id`).
- **Config-first:** расписания, лимиты, пороги качества, параметры генерации, правила публикации —
  в конфиге, не в коде.
- **Plugin:** новый LLM/генератор/экспортёр/источник — через провайдер-абстракцию, без изменения ядра.
- **Error philosophy:** обнаружить → записать → классифицировать → обработать → не ронять систему.

## RELEASE CRITERIA

Готово только если: все сервисы стартуют · миграции проходят · основные сценарии работают ·
тесты зелёные · документация актуальна · backup настроен · мониторинг активен.

## FINAL GOAL (пользовательский сценарий)

Добавить канал → создать/выбрать персону → загрузить примеры и KB → настроить расписание →
указать модели → запустить. Дальше — автономная работа в рамках правил + инструменты контроля,
анализа и развития.

## КОНСОЛИДИРОВАННЫЕ АДДЕНДУМЫ К СХЕМЕ (Часть 4)

Свести в единый DDL при генерации моделей (иначе схема живёт в 4 документах):

- **Расширение enum `role`:** +`editor`, +`analyst` (Часть 10).
- Проверить: все `vector`-колонки одной платформенной размерности (текст) / CLIP-размерности (изображения).

## ⚠️ ОТКРЫТЫЕ РЕШЕНИЯ — за владельцем, не за Claude Code

Два выбора спека сознательно **не** делает, потому что они меняют объём и риск:

1. **MTProto read-only stats-адаптер (да/нет).** Без него per-post views/ER недоступны →
   self-learning слабый, дашборд без engagement. С ним — полноценный сигнал, но доп. интеграция и
   операционный риск (сессия как секрет). Влияет на Части 5, 10, 11, 12.
2. **Целевая среда развёртывания:** одна VM / облако / оркестрация. Определяет reverse proxy,
   secret manager, пул соединений, стратегию бэкапа. Влияет на Часть 12.

Пока не выбрано — реализация идёт по дефолтам (без MTProto; одиночная VM + Compose + Caddy).

## MASTER PROMPT ДЛЯ CLAUDE CODE

> Роль и правила — из [Части 1A](01-system-prompt.md) (builder). Ниже — операционная выжимка.

Ты строишь **модульный монолит** (Часть 2), не микросервисы. Источник истины по любому
конфликту документов — **реестр решений выше**. Порядок реализации — из IMPLEMENTATION ORDER.

Обязательные инварианты на каждом шаге:

1. Слои не смешиваются (Часть 3); доменный пакет не открывает сессию БД.
2. Любой внешний вызов (LLM/Image/Embed/Telegram) — через интерфейс + фабрику + **фейк**;
   вся система запускается и тестируется **offline**.
3. Пайплайн — 5 задач в очереди с continuation-chaining; состояние — в Postgres.
4. Каждый пост проходит **hard gates** (Часть 5); низкокачественное не публикуется.
5. Изоляция канала — `WHERE channel_id` в каждом запросе (кроме Global Memory).
6. Секреты — env/secret manager, никогда в код/логи; пороги/лимиты — конфиг, не «магия».
7. Тесты пишутся вместе с кодом; чистая логика — юнит, БД/сеть — за `RUN_INTEGRATION=1`.
8. Не реализовывать спекулятивное (плагин-загрузчики, видео, K8s) без реальной потребности.
