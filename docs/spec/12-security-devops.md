# Часть 12. Security, DevOps & Production Infrastructure

> Объединяет исходные Части 12 (Docker) и 13 (Security). Продолжает
> [Часть 11](11-analytics-self-learning.md). Реализует инфраструктуру под модульный монолит
> ([Часть 2](02-architecture.md)) с несколькими точками входа ([Часть 3](03-repository-structure.md)).

## GLOBAL OBJECTIVE

Безопасность · надёжность · масштабируемость · отказоустойчивость · воспроизводимость окружения ·
удобство сопровождения.

## ENVIRONMENTS

Development · Testing · Staging · Production — каждое со своими env, БД, конфигом, ключами,
журналами, мониторингом. Продвижение только через CI/CD (ниже).

## CONFIGURATION & SECRET MANAGEMENT

Все настройки — вне кода (`.env`, конфиги, секрет-хранилище). **Секреты в репозитории запрещены.**

Секреты: API-ключи · токены Telegram · ключи LLM · строка подключения БД · ключи генераторов
изображений · сервисные учётки. Правила: грузятся только при запуске · **не в журналах**
(маскирование) · **не в панели в открытом виде** (write-only, Часть 10).

> **Прод ≠ `.env`-файл.** В production секреты — через **Docker secrets / облачный secret
> manager**, не plaintext-файл на диске. БД-доступ — **least-privilege роль** (не суперюзер).

---

## ⚠️ DOCKER: контейнеры — это роли ОДНОГО образа, не микросервисы

Черновик перечисляет `api / scheduler / worker / admin-panel` как контейнеры. По решению Части 2
это **не** отдельные сервисы — это **один и тот же образ**, запущенный с разными командами
(Часть 3: `main.py` / `scheduler/run.py` / `workers/run.py`):

```text
приложение (один образ):
  api        → uvicorn app.main            (+ admin-panel HTMX, Часть 10)
  scheduler  → python -m app.scheduler.run (продюсер задач)
  worker     → python -m app.workers.run   (исполнитель, масштабируется ×N)
инфраструктура:
  postgres (pgvector)   redis   nginx/caddy (reverse proxy)
```

`admin-panel` отдаётся тем же `api`-контейнером (Часть 10), отдельный не обязателен. Доп. сервисы
добавляются без изменения схемы.

### DOCKER PRINCIPLES

Каждый контейнер: одна функция · собственный healthcheck · минимальный размер (slim/distroless) ·
независимый запуск · корректное завершение (graceful shutdown — воркер дорабатывает текущую
задачу, не бросает её на середине).

---

## REVERSE PROXY / HTTPS / NETWORK

- **Reverse proxy** (рекомендую **Caddy** — авто-TLS из коробки, проще nginx+certbot): HTTPS,
  маршрутизация, rate-limit, сжатие, security-заголовки.
- **HTTPS** обязателен для всех внешних соединений; авто-обновление сертификатов заложено.
- **Least exposure:** наружу торчит **только** proxy. `postgres`/`redis`/`worker`/`scheduler`
  — только во внутренней docker-сети, **не** публикуются в интернет.

---

## DATABASE SAFETY & MIGRATIONS

Пул соединений (async, ограничен; при масштабе — pgbouncer) · транзакции · миграции · версии
схемы. **Ручное изменение структуры на проде запрещено** — только Alembic.

> **⚠️ 24/7 + миллионы строк → expand-contract.** Наивный `ALTER`/индекс на горячих таблицах
> (`memory`, `analytics_snapshots`, `api_usage`) **залочит** их и остановит публикации. Схемные
> изменения на больших таблицах — паттерном **expand → migrate → contract** (добавить новое,
> двойная запись, бэкофилл, переключение, удаление старого; индексы — `CREATE INDEX CONCURRENTLY`).
> Это условие требования «работать 24/7».

## BACKUP / RESTORE

- **Backup:** БД (`pg_dump` + желательно PITR/WAL), изображения (**object storage**, Часть 6),
  конфиги, KB, вектора (часть дампа БД), метаданные. Ежедневные/еженедельные/месячные, срок
  хранения настраивается.
- **Restore:** проверяется **регулярно** — полная система / только БД / отдельный канал /
  документы / изображения.

> **Непроверенный бэкап = отсутствие бэкапа.** Восстановление на staging — часть регламента,
> не «когда-нибудь».

---

## LOGGING / LOG LEVELS / AUDIT

Единый **структурированный (JSON)** формат: время · уровень · сервис · request/`task_id` ·
`channel_id` · событие. Уровни: DEBUG/INFO/WARNING/ERROR/CRITICAL.

**Audit log отдельно** (таблица `audit_log`, аддендум Части 10): авторизация · изменения
настроек/ролей/конфигурации · ручные публикации · удаление данных.

## MONITORING / ALERTING / HEALTH CHECKS

- **Monitoring:** доступность сервисов · нагрузка · память/CPU · доступность БД · размер очередей
  · ошибки API/Telegram/изображений.
- **Health checks:** **liveness** (процесс жив) ≠ **readiness** (зависимости доступны) — отдельные
  эндпоинты; Docker healthcheck + app-эндпоинты; питает `health_check`-задачи (Часть 8) и Health
  Dashboard (Часть 10).
- **Alerting:** остановка Scheduler · недоступность БД · неудачный backup · массовые ошибки
  публикации · переполнение диска.

> **Кто сторожит сторожа:** алертинг не должен зависеть только от системы, которую мониторит.
> Мёртвый scheduler не сообщит о себе сам → **внешний dead-man's-switch** (external uptime-пинг /
> heartbeat), иначе тихий отказ незаметен.

---

## RESOURCE LIMITS & SCALING

Лимиты на контейнер: память · CPU · число процессов · число соединений — чтобы сервисы не влияли
друг на друга.

Горизонтальное масштабирование (Часть 2): больше `worker`-контейнеров, разнесение по узлам,
масштаб `api`/генерации — без изменения бизнес-логики.

> **⚠️ Мульти-воркер ломает in-process лимитер.** Семафор конкурентности из Части 8, живущий
> **в памяти процесса**, при N воркер-контейнерах **не ограничивает суммарную** нагрузку на
> провайдера → вернутся 429. Значит rate-limiter/семафор обязан быть **распределённым (Redis
> token-bucket)**, общим для всего флота. Это условие масштабирования, а не оптимизация.

## FAILURE RECOVERY

Отказ сервиса: остальные работают · задача → очередь ретраев (`deferred`, Часть 8) · событие
зафиксировано · уведомление. Состояние — в Postgres, переживает перезапуск.

## CI/CD

Пайплайн (деплой только после **всех** проверок):

1. Формат (`ruff format`/`black`).
2. Статический анализ (`ruff`, `mypy` — типизация обязательна, Часть 3).
3. Тесты (`pytest`: юнит всегда; интеграционные за `RUN_INTEGRATION=1`).
4. Сборка контейнеров.
5. **Проверка миграций** (alembic: генерируются/применяются/не деструктивны неожиданно).
6. Развёртывание.

## TESTING

Юнит · интеграционные (за флагом) · API · миграций · основных сценариев. Чистая логика (chunking,
backoff, similarity, правила валидации) — юнит; пути с БД/сетью — интеграционные; домен — через
фейки провайдеров (offline, Часть 2/3).

## DEPENDENCY MANAGEMENT

**Фиксированные версии** (lock-файл `uv`). Обновления — через тестирование перед продом.

## DEPLOYMENT / DOCUMENTATION

Развёртывание **воспроизводимо**: новый сервер — по документированной процедуре с минимумом
ручных шагов. Инструкции для прод: первый запуск · обновление · восстановление · backup ·
перенос на новый сервер · диагностика.

---

## SECURITY PRINCIPLES

Минимально необходимые права (least privilege) · валидация входных данных · защита панели (RBAC
на бэкенде, Часть 10) · защита API · защита журналов (маскирование секретов) · защита бэкапов
(шифрование, ограниченный доступ).

> **MTProto stats-адаптер (Часть 11) — под особый контроль:** отдельная сессия/учётка,
> хранение session-файла как секрета, только на чтение, изоляция в своём контейнере/провайдере.

## FUTURE EXTENSIBILITY

Заложить (без спекулятивной реализации сейчас): переход в облако, оркестрация (K8s), доп.
сервисы, масштаб без изменения логики приложения.

## SYSTEM DIAGNOSTICS (твоё дополнение)

Периодически: проверка конфигурации · зависимостей · поиск устаревших компонентов · анализ
производительности · рекомендации по оптимизации.

> Позиционирование: это **ops-дополнение** к runtime health checks — сторона «свежесть
> зависимостей / валидность конфига / деградация производительности», не дублирует Health
> Dashboard, а дополняет его. Пересекается с Error Analytics (Часть 11) — переиспользует её данные.

## Reconciliation

- Контейнеры `api/scheduler/worker` — **роли одного образа**, не микросервисы (Часть 2/3).
- Rate-limiter — **распределённый (Redis)**, иначе мульти-воркер выбивает 429.
- Схемные миграции на горячих таблицах — **expand-contract** + `CREATE INDEX CONCURRENTLY` (24/7).
- Секреты в проде — secret manager, не `.env`; БД — least-privilege роль.
- Наружу — только reverse proxy (auto-TLS); БД/redis/воркеры не публикуются.
- Restore тестируется регулярно; алертинг — с внешним dead-man's-switch.
- MTProto-адаптер (Часть 11) — под усиленным контролем секретов/изоляции.
