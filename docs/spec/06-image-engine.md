# Часть 6. Image Engine (автоматическая генерация фотографий)

> Продолжает [Часть 5](05-ai-engine.md). Окна и запреты повторов заданы в
> [Части 1](01-system-prompt.md) (`IMAGE_WINDOW=30`, гардероб ≥3, палитра ≥2); модель
> CLIP-эмбеддинга платформенно зафиксирована ([Часть 4](04-database-design.md)).

## GLOBAL OBJECTIVE

Полностью автоматическая генерация изображений для всех каналов. Каждый кадр выглядит по стилю
канала — например, «снято на современный смартфон живым человеком», либо иной стиль из настроек.

---

## ⚠️ Центральный технический риск: постоянство внешности актёра

Черновик требует «соответствия персонажу» — тот же человек изо дня в день. **Одним текстовым
промптом это недостижимо:** text-to-image по словесному описанию генерирует каждый раз **новое
лицо**. Это make-or-break всего замысла «канал ведёт один узнаваемый персонаж».

**Что реально даёт постоянство лица (обязательно к реализации):**

- **conditioning по референсам** актёра: IP-Adapter / face-embedding / img2img от опорных
  изображений — не просто текст;
- либо **per-actor LoRA / fine-tune** (дороже в подготовке, стабильнее в проде);
- **фиксированный seed** сам по себе НЕ даёт того же человека при смене промпта — только
  стабилизирует шум; идентичность держат референсы/веса.

**Следствия для архитектуры:**

- `actors.reference_images_folder` — не «дополнительно», а **вход генерации**: интерфейс
  провайдера обязан принимать опорные изображения/identity-эмбеддинг.
- **Провайдер обязан поддерживать identity-conditioning.** Провайдеры без него (чистый
  text-to-image) для каналов с постоянным персонажем непригодны — это критерий выбора в
  `image_provider`, а не деталь.
- **Мульти-актёрные сцены** (семья, группа) — постоянство нескольких лиц в одном кадре ещё
  сложнее; помечаем как отдельную, более рискованную ветку (возможно — композитинг из
  одиночных генераций, а не один кадр).

> Без этого блока вся «библиотека актёров» превращается в случайные лица. Это первое, что
> должно быть доказано на прототипе провайдера.

---

## Юридика/политики провайдеров (операционный флаг)

- Провайдеры фотореалистичных людей часто **отклоняют** запросы по контент-политике → отказ
  провайдера обрабатывается как сбой: fallback-провайдер или деферал, **не** падение.
- Актёры — **вымышленные лица**; система не должна воспроизводить внешность реальных людей
  (референсы — только сгенерированные/лицензированные, не фото реальных персон).

---

## IMAGE PIPELINE

Стадия `generate_image` из Части 5 (одна задача очереди), внутри:

```
load channel/persona/actors → load previous images + wardrobe + locations + scene history →
choose new scene (диверсити ДО генерации) → build prompt → build negative prompt →
generate (с identity-conditioning) → validate → similarity check → quality check → save
```

Публикация — отдельной задачей `publish` (Часть 7).

---

## Разнообразие задаётся ДО генерации, проверяется ПОСЛЕ

Ключевой принцип экономии: изображение платное и медленное. Нельзя генерировать вслепую и
браковать. Поэтому:

1. **Scene selection (дёшево, детерминированно):** выбрать локацию/одежду/позу/ракурс/эмоцию,
   **исключив** значения из окон (`IMAGE_WINDOW=30` для композиции/ракурса, гардероб ≥3,
   палитра ≥2) — по метаданным прошлых кадров в БД. Разнообразие обеспечивается здесь.
2. **Post-generation verification (дорого):** сгенерированный кадр сверяется CLIP-эмбеддингом;
   срабатывает только как страховка, а не основной механизм.

---

## Каскад проверки похожести (три РАЗНЫХ механизма)

Черновик смешивает их — разводим, они ловят разное:

| Механизм | Что ловит | Стоимость |
|---|---|---|
| **Perceptual hash (phash)** | почти-идентичные пиксели (дубль) | дёшево |
| **Метаданные сцены** | повтор локации/одежды/позы/ракурса/эмоции/фона по окнам | дёшево (SQL) |
| **CLIP-эмбеддинг** (`images.embedding vector(512)`) | визуально-семантическое сходство | дорого |

phash **не** ловит «то же кафе в другой одежде» — это работа метаданных. CLIP ловит семантику.
При превышении порога — регенерация (см. ниже).

---

## ACTOR LIBRARY

На канал — своя библиотека (изоляция по `channel_id`, Часть 4). На актёра: uuid, имя, пол,
возраст, рост, телосложение, черты лица, цвет глаз, причёска, цвет волос, любимая/стиль одежды,
национальность, описание внешности, **базовый промпт**, **negative prompt**,
**папка референсов (вход генерации!)**, примечания.

Мульти-актёрность: 1 человек · 2 · семья · группа · клиенты · коллеги · друзья · встречи
(с оговоркой о сложности постоянства лиц выше).

## LOCATION LIBRARY

Каталог на канал: дом, кафе, офис, переговорная, пляж, набережная, парк, самолёт, авто,
ресторан, спортзал, горы, мечеть, улица, отель, терраса. На локацию: описание, референсы,
частота использования, время последнего использования (для диверсити-окон).

## WARDROBE

Гардероб на актёра; вещь: тип, цвет, бренд (если важно), стиль, сезон, формальность, частота.
Один и тот же образ подряд запрещён (окно ≥3, Часть 1).

## SCENE ENGINE

Кадр = локация · поза · одежда · освещение · время суток · ракурс · фокусное · настроение ·
эмоция · занятие.

### DAILY SCENES — привязка к времени публикации

Сцена согласуется со **временем слота из расписания** (Часть 8): подъём/кофе/работа/встреча/
обед/ноутбук/поездка/закат/ужин/дом. Случайные сцены без учёта времени суток запрещены —
`scheduled_at` определяет правдоподобный набор сцен.

## CAMERA / IMAGE STYLE PROFILE

Профиль канала задаёт: тип камеры (iPhone 15 Pro / Pixel / Galaxy Ultra / беззеркалка /
кинематограф), фокусное, освещение, контраст, цветовую температуру, стиль обработки,
детализацию, соотношение сторон. Хранится в профиле канала.

---

## PROMPT BUILDER / NEGATIVE PROMPT

Промпт собирается **динамически** из блоков: персона → локация → одежда → действие → эмоция →
композиция → освещение → стиль камеры → детали → ограничения. Плюс **опорные изображения
актёра** как отдельный вход (см. риск выше). Negative prompt тоже собирается автоматически из
**настраиваемого конфига** (артефакты, лишние объекты, несоответствия стилю) — под конкретного
провайдера. Один статический промпт на все случаи запрещён.

## IMAGE VALIDATOR

После генерации проверяются: лицо, руки, глаза, одежда, артефакты, реалистичность,
**соответствие актёру** (сравнение face-эмбеддинга с референсом — иначе «соответствие»
не проверяемо). Не прошёл → регенерация.

---

## RETRY / REGEN — согласование с Частью 1/5

Черновик: «максимум 5 попыток». Разводим, как для текста, и учитываем стоимость:

- **`IMAGE_MAX_REGEN` (деф. 3, конфигурируемо до 5)** — регенерации ради **качества/уникальности**
  (плохие руки/лицо, слишком похоже). Каждая попытка — **платный вызов**, поэтому дефолт ниже,
  чем хотелось бы; при новой попытке меняем композицию/одежду/позу/ракурс.
- **`MAX_RETRIES=5`** (Часть 1) — только инфраструктурные сбои (провайдер недоступен/429).
- Исчерпан `IMAGE_MAX_REGEN` без валидного кадра → пост уходит **в ревью владельцу** (или
  публикуется без фото, если канал это разрешает) — но **не** бесконечная генерация.

---

## STORAGE

Сохранять: оригинал, миниатюру, промпт, negative prompt, настройки, метаданные, CLIP-эмбеддинг,
phash. Метаданные и вектор — в `images` (Часть 4); файлы — на диск/**объектное хранилище**.

> **Флаг масштаба:** «сотни тысяч изображений» на локальном диске (`storage/images/`) не тянется
> в проде — для роста нужен S3-совместимый object storage, а `storage_path` хранит ключ объекта.
> На старте локально допустимо; порог перехода фиксируется в Части 12.

## IMAGE QUALITY SCORE

Итог = реалистичность + уникальность + соответствие актёру + соответствие стилю канала +
отсутствие артефактов. Часть — **hard gate** (соответствие актёру, уникальность, отсутствие
грубых артефактов), часть — soft (для выбора лучшего из кандидатов, аналогично тексту).
Публикация только после hard gates.

## FUTURE EXTENSIBILITY

Заложить возможность (но **не реализовывать спекулятивно**): короткие видео, обложки, карусели,
сторис, автообработка, интеллектуальное кадрирование, адаптация под Telegram/Instagram/X.
Вводится через тот же интерфейс провайдера — по реальной потребности.

---

## Reconciliation

- Постоянство лица = референсы/identity-conditioning, **не** текст и не seed — критерий выбора провайдера.
- Дубликаты изображений = 3 механизма (phash / метаданные / CLIP), не один.
- Разнообразие — на выборе сцены (до генерации), CLIP — верификация после.
- `IMAGE_MAX_REGEN` (качество, деф.3) ≠ `MAX_RETRIES` (инфра, 5); каждая регенерация платная.
- CLIP-эмбеддинг — платформенно фиксирован (Часть 4), как и текстовый.
