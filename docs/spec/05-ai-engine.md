# Часть 5. AI Engine (ядро системы)

> Продолжает [Часть 4](04-database-design.md). Здесь описано, как строится генерация текста.
> Пороги и каскады из [Части 1](01-system-prompt.md) и [Части 2](02-architecture.md) не
> переопределяются — уточняются механикой.

## GLOBAL OBJECTIVE

AI Engine — главный интеллект платформы: выбирает тему, собирает контекст, пишет пост,
проверяет сам себя, принимает решение о публикации, учится на статистике. Остальные модули —
исполнители.

## MAIN RESPONSIBILITIES

Выбор темы · контент-план · текст · заголовок · CTA · эмоция · длина · анализ истории · поиск
повторов · промпт изображения · самопроверка · переписывание · анализ успешности · адаптация стиля.

## AI PIPELINE → задачи очереди

Порядок стадий фиксирован, но **«никаких исключений» относится к порядку, а не к отказам**:
любая стадия может упасть → ретрай/деферал по политике Части 1 (это не нарушение пайплайна).

Стадии группируются в типы задач из Части 2/4 (не по одной задаче на строку — иначе overhead):

| Задача (`task_type`) | Что внутри |
|---|---|
| `generate_text` | load persona/memory → topic → outline → draft → **self-review↔rewrite loop** |
| `validate` | детерминированные gate-проверки (грамматика, язык, длина, дубликаты, стиль, эмоция) |
| `generate_image` | промпт изображения → генерация → проверка похожести (Часть 6) |
| `publish` | финальная валидация → публикация (Часть 7) |
| `collect_metrics` | сбор аналитики (Часть 10) → сохранение в память |

Цикл self-review ↔ rewrite живёт **внутри** `generate_text` (это один логический юнит), а не
как отдельные задачи — иначе цикл размазан по очереди и теряет промежуточные кандидаты.

## Сборка контекста — ключевое разведение

Черновик говорит «загрузить последние 500 постов». **Их нельзя класть в промпт** — это тысячи
токенов и деньги на каждый пост. Разводим два разных механизма:

- **Окно сравнения (500)** — это `history_window` для проверки уникальности. Работает на
  **векторах** (косинус к эмбеддингам в `memory`), в промпт **не попадает**, токенов не тратит.
- **Few-shot в промпте** — **малый K = 3–5** лучших/релевантных примеров, отобранных через RAG
  (retriever → reranker), плюс `persona.best_examples`. Только это идёт в контекст модели.

Что грузится перед постом (в память процесса, не всё в промпт):

- в промпт: персона, правила стиля, текущая тема, ограничения, K few-shot примеров, топ-N
  «любимых слов»/«запрещённых конструкций»;
- только для проверок (не в промпт): окно из 500 эмбеддингов, история изображений, использованные
  темы/CTA, эмоц. профиль, успешные/неудачные метрики.

**Бюджет контекста** фиксируется: `MAX_CONTEXT_TOKENS` на канал; сборщик промпта обрезает
few-shot по бюджету, приоритет — самые релевантные примеры.

---

## PERSONA LOADING

Перед каждым постом грузится `personas` (Часть 4): характер, возраст, биография, манера речи,
религиозные особенности, образование, род деятельности, типичные истории, отношение к
подписчикам, словарь, обращения, правила жанров, `best_examples`. Текст пишется **от лица
конкретного человека**, а не «в стиле».

---

## TOPIC GENERATION + DIVERSITY

AI сам выбирает тему (не получает готовую): последние темы → исключить недавние → популярные →
расписание / день недели / время суток / сезон / праздники / события → выбор новой темы.

**Diversity как жёсткие ограничения (не пожелание):**

- нельзя 3 дня подряд один `content_type` (мотивация/продажа);
- нельзя повторить CTA из последних N;
- нельзя повторять вступления/выводы/истории (проверка дубликатов, см. ниже).

Реализация — не «на глаз»: анализатор читает последние публикации канала и формирует
**список запретов** (`forbidden_this_run`), который передаётся в промпт и в `validate`.

### CONTENT TYPES

утренний/вечерний блог · личная история · рабочий день · мотивация · история клиента/успеха ·
новости · образовательный · FAQ · продающий (мягкий/жёсткий) · разбор ошибки · закулисье ·
цитата · мини-дневник · ответ подписчику. Тип — одна из «рук» bandit (см. Self-learning).

## STYLE ENGINE

Стиль канала = ритм · лексика · структура · эмоции · длина предложений · частота абзацев ·
частота эмодзи · частота CTA. Хранится в `personas` + `channel_settings`, применяется через
промпт-билдер и проверяется в `validate`.

## SELF-REVIEW — генератор ≠ судья

Модель, судящая свой вывод в том же вызове, ненадёжна. Разделяем на два независимых механизма:

1. **Rule-based gates (детерминированно, дёшево, бинарно)** — грамматика, язык, длина,
   стоп-лист, структура, повтор CTA/вступлений. Не прошёл → мгновенный `fail`, без LLM.
2. **LLM-judge (отдельный вызов, отдельный промпт)** — логичность, естественность, плавность,
   интерес, эмоции, убедительность, **человечность**. Оценивает по рубрике 0–100.

Судья — **не тот же запрос**, что генерация; может быть дешевле моделью (см. Cost Control).

---

## SELF-REWRITE — согласование с Частью 1

Черновик: «максимум 5 попыток». Часть 1: `MAX_REWRITES=3`. Это разные вещи — разводим
терминологию окончательно:

- **`MAX_REWRITES = 3`** — переписывания ради **качества** (не прошёл self-review/дубликаты).
- **`MAX_RETRIES = 5`** — повторы при **инфраструктурных сбоях** (провайдер недоступен, 429).

**Стратегия «оставить лучший» (best-of-N с гейтом):**

- итерируем до первого кандидата, прошедшего все gates + порог judge → берём его;
- если за `MAX_REWRITES` ни один не прошёл → берём **лучший по quality-score** и отправляем
  на **ревью владельцу** (Часть 1: низкокачественное не публикуется автоматически);
- каждый кандидат оценивается, лучший сохраняется как fallback (не теряем работу модели).

---

## DUPLICATE DETECTOR — каскад дёшево → дорого

Порядок от самого дешёвого фильтра к самому дорогому (ранний выход при совпадении):

1. **N-gram / trigram Jaccard** (детерминированно, без сети) — грубый префильтр.
2. **Sentence / paragraph similarity** — на эмбеддингах предложений/абзацев.
3. **Embedding similarity** поста целиком — косинус к окну `history_window`.
4. **Story / CTA similarity** — эмбеддинги соответствующих полей.

При превышении `similarity_threshold` (0.85, Часть 1) — **полностью переписать** (в пределах
`MAX_REWRITES`).

---

## HUMANIZATION

Убрать всё «машинное»: слишком правильные предложения, идеальную структуру, одинаковые размеры
абзацев, канцеляризм, типичные AI-фразы, академизм. Механика — не пожелание:
**стоп-лист** (rule-based gate) + **judge-порог человечности `HUMANNESS_MIN=75`** (Часть 1).
Ниже порога → rewrite.

## STORY / EMOTION / CTA ENGINES

- **Story:** каждый блог — истории, наблюдения, эмоции, детали, контекст, вывод.
- **Emotion:** каждому посту назначается эмоция (спокойствие/радость/благодарность/мотивация/
  грусть/ностальгия/вдохновение/любопытство/уважение/надежда); проверяется в `validate`.
- **CTA:** нельзя один и тот же постоянно — выбор из пула (вопрос / в личку / мнение /
  прошлый пост / сохранить / переслать), с запретом повтора из последних N.

---

## LEARNING & SELF-LEARNING — это bandit, а не «увеличить вероятность»

После публикации приходит статистика (views, ER, CTR, репосты, комментарии, динамика). Правило
«лучший стиль чаще, худший реже, но не зациклиться» — это **многорукий бандит на канал**:

- «руки» = комбинации (`content_type`, эмоция, структура, длина, CTA);
- политика: **epsilon-greedy / Thompson sampling** с **полом исследования** (`epsilon_min`),
  который гарантирует разнообразие и не даёт схлопнуться в один шаблон;
- награда = нормированная метрика вовлечённости.

**Честная оговорка:** сигнал приходит с задержкой в дни и шумный. Поэтому обновление —
**медленное и регуляризованное** (сглаживание, минимум наблюдений на руку перед реакцией),
иначе система переобучится на шум. Параметры обучения — платформенные, с оверрайдом на канал.

## MULTI-LLM + FALLBACK (конкретные tier'ы)

Каждый провайдер реализует общий интерфейс (`base_provider` + фабрика). Замена модели не трогает
бизнес-логику. Каскад fallback из Части 2, теперь с моделями:

1. **Primary** (тело поста, ключевые продающие): `claude-opus-4-8`.
2. **Fallback tier** (при недоступности/429): `claude-haiku-4-5` или кросс-провайдер (OpenAI).
3. Недоступны оба → **reschedule** публикации.
4. Reschedule невозможен → **уведомить владельца**.

> Embedding-модель здесь **не выбирается** — она платформенно зафиксирована (Часть 4), иначе
> ломается векторный индекс.

## COST CONTROL — таблица роутинга

Простые задачи — дешёвой моделью, ключевые — мощной. Роутинг по типу задачи:

| Задача | Модель | Почему |
|---|---|---|
| Тело поста, продающие | `claude-opus-4-8` | максимум качества |
| Заголовок, CTA, выбор темы, классификация | `claude-haiku-4-5` | дёшево, достаточно |
| LLM-judge (человечность/стиль) | `claude-haiku-4-5` | судить дешевле, чем писать |
| Эмбеддинги | платформенная embedding-модель | фиксирована (Часть 4) |

Это позволяет масштабировать на 1000 каналов без взрывного роста расходов. Стоимость каждого
вызова пишется в `api_usage` (Часть 4).

## QUALITY SCORE — финальный гейт

Итоговая оценка = взвешенная сумма независимых критериев; часть — **жёсткие gate**
(бинарные, блокируют публикацию), часть — **мягкие score** (влияют на выбор лучшего кандидата):

| Критерий | Тип | Источник |
|---|---|---|
| язык / длина / стоп-лист | hard gate | rule-based |
| уникальность (`< similarity_threshold`) | hard gate | duplicate cascade |
| человечность (`≥ HUMANNESS_MIN`) | hard gate | LLM-judge |
| соответствие стилю | soft + порог | LLM-judge |
| читаемость | soft | rule-based (напр. индекс удобочитаемости) |
| связность | soft | LLM-judge |
| эмоциональность | soft | LLM-judge |
| качество CTA | soft | LLM-judge |

**Публикация допускается только при прохождении всех hard gates.** Иначе — rewrite или ревью
владельцу. Веса мягких критериев — платформенные, оверрайд на канал.

## PROMPT BUILDER

Промпт **собирается динамически** из модулей: профиль канала + персона + тема + расписание +
память (few-shot) + успешные примеры + ограничения (`forbidden_this_run`) + правила стиля.
**Один большой статический промпт запрещён.** Сборщик соблюдает `MAX_CONTEXT_TOKENS`.

---

## Reconciliation (что здесь согласовано)

- `MAX_REWRITES` (качество, 3) vs `MAX_RETRIES` (инфра, 5) — окончательно разведены.
- «500 постов» = окно векторного сравнения, **не** контент промпта; в промпт — few-shot K=3–5.
- Self-review = rule-based gates + отдельный LLM-judge, не самопроверка в том же вызове.
- Self-learning = bandit с полом исследования + медленное обновление (защита от шума).
- Fallback/роутинг — конкретные модели; embedding-модель платформенно зафиксирована.
